# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Development
npm run dev          # Start dev server on port 3000

# Build & Production
npm run build        # Build (copies static + public into standalone)
npm start            # Run production build (standalone mode)

# Lint
npm run lint         # ESLint

# Database (Prisma + PostgreSQL — required, see "Backend" below)
npm run db:push      # Push schema to DB (no migration history — fine for dev)
npm run db:migrate   # Create/run a migration (use once schema is stable)
npm run db:generate  # Regenerate the Prisma client after schema.prisma changes
npm run db:seed      # Seed PricingRate rows (prisma/seed.ts)
npm run db:reset     # Drop + recreate the DB, reapply migrations, reseed
```

There are no test commands — this project has no test suite.

## Architecture

Next.js 16 / React 19 / TypeScript, App Router. Two things coexist:

1. **The marketing/tool shell** — `src/app/page.tsx` renders `portal-main.tsx`'s `App`, which owns Home/PCB Order/Panelization/Assembly/Shop/Blog via client-side `useState('home')`, **not** real Next.js routes. This is legacy from before the backend existed; don't migrate it wholesale, just be aware `page` state ≠ URL here.
2. **Real routes with a database** — auth, orders, messaging, and admin all use actual App Router pages/API routes backed by PostgreSQL via Prisma. See "Backend" below.

### Gerber / Panelization data flow (client-side, no DB)

1. **Import** — User uploads `.gbr`/`.drl` files or a ZIP. `store.ts:addLayer` / `addLayersFromZip` parse each file and call `gerberToSvg()` from `gerber-svg.ts`, which dispatches to a Web Worker.
2. **Parse** — `gerber-parser.ts` produces `GerberLayer` data with bounds and draw commands, used for panelization + export math. It holds **both** parsers: `parseGerber` (custom RS-274X) and `parseExcellonDrill` (Excellon drill), dispatched on `isExcellonDrillFile`. Drill layers additionally carry a `drillMeta` field (resolved unit / digits / zero suppression / tool + hole counts / where the format came from) which the Layers panel displays.
3. **SVG render** — `src/workers/gerber-worker.ts` runs `@tracespace/parser` → `@tracespace/plotter` → `@tracespace/renderer` and returns an `svgFragment` + bounds. Fully client-side; no server roundtrip.
4. **Layer detection** — Layer type and side are inferred from Gerber's `TF.FileFunction` attribute first, then filename heuristics in `gerber-analysis.ts:detectLayerType/detectLayerSide` (re-exported by `store.ts` — the two Gerber consumers, the Panelization tool and the PCB Order quote flow, share this logic rather than duplicating it). The filename fallback matters more than it sounds: PentaLogix ViewMaster exports (confirmed on a real customer set) carry no `TF.FileFunction` attribute at all, so a file named e.g. `_MSK-TOP.art`/`_SLK-BOT.art` depends entirely on the heuristic recognizing the `MSK`/`SLK` abbreviations for mask/silk — without that, `TOP`/`BOT` in the same filename falls through to the bare-copper catch-all and every mask/silk layer renders as copper.
5. **View** — `gerber-viewer.tsx` is an SVG canvas with pan/zoom. On the **Panel Config** tab it builds a `<defs>` of one geometry per layer and `<use>`s it for every PCB position so panel-mode DOM size stays constant in `rows × cols`.
6. **Panelization** — `panelization-engine.ts` computes a `PanelResult` from PCB dimensions + `PanelConfig`. PCB dimensions come from the layer with the largest bounding area (or the explicit `outline` layer if present).
7. **Export** — `gerber-exporter.ts` generates RS-274X Gerber for every layer in the panel plus Excellon drill output, bundled into a ZIP via JSZip + file-saver.

### Backend (PostgreSQL + Prisma + Auth.js v5)

Requires a running Postgres and a populated `.env` (`DATABASE_URL`, `AUTH_SECRET`, `APP_URL`, `RESEND_API_KEY`, `EMAIL_FROM` — see `.env.example`). Schema: `prisma/schema.prisma`.

- **Auth** — Auth.js v5 (`next-auth@beta`), Credentials provider, Prisma adapter, JWT sessions. Config is split across `src/lib/auth.config.ts` (Edge-safe subset — no Prisma/bcrypt — used by `middleware.ts`) and `src/lib/auth.ts` (full config with the adapter + provider, used everywhere else). **Don't import `auth.ts` from middleware** — it pulls in the Prisma adapter, which breaks on the Edge runtime. Roles: `CUSTOMER` / `ENGINEER` / `ADMIN`. Password reset is fully custom (`PasswordResetToken` model + `src/lib/email.ts` via Resend) since Credentials auth has no built-in flow. Real routes: `/login`, `/register`, `/forgot-password`, `/reset-password`.
- **Pricing** — `src/lib/pricing-engine.ts` exports `calculatePcbQuoteV2`, a pure function (no DB import) that resolves a quote from a `PricingRatesMap`. Rates live in one generic `PricingRate` table (`category` + `key` + `value` + `unit`), editable at `/admin/pricing`, so raw-material cost changes don't require a redeploy. `src/app/api/quote/route.ts` fetches active rates, builds the map via `buildRatesMap`, and calls the pure function. `prisma/seed.ts` seeds initial rates transcribed from the old hardcoded constants in `src/lib/pcb-pricing.ts` (now superseded, kept for reference — not deleted). **Orders store a full snapshot** of the resolved breakdown in `Order.priceBreakdown` (JSON) at creation time — editing a `PricingRate` later must never change an already-placed order's price; if you touch the pricing flow, preserve this.
- **Orders** — `src/app/api/orders/route.ts` (list/create) and `.../[id]/route.ts` (get/PATCH status). Creating an order also creates its `MessageThread` in the same transaction. Customer view: `/orders/[id]`. Staff view: `/admin/orders/[id]` (adds a status-change control). `Order.reference` is a date-encoded, human-readable ID (`PCB-YYYYMMDD-NNNN`, day boundary in IST since the business is Bangalore-based) generated by `src/lib/order-reference.ts`'s `generateOrderReference()` — always call it with the transaction client (`tx`, not `db`), not just for consistency but because it must run inside the same transaction as `Order.create` so a rollback also undoes the counter increment (`OrderSequence` table, one row per day, incremented via an atomic Postgres upsert). Never derive the sequence number by counting existing rows — concurrent requests would race and collide.
- **Messaging** — Polling-based (no WebSockets), 10s interval via `@tanstack/react-query`'s `refetchInterval`. One `MessageThread` per order (or a standalone `GENERAL_INQUIRY` thread). Shared UI: `src/components/messaging/message-thread.tsx`, used by both the customer and staff order-detail pages. API: `src/app/api/messages/threads/route.ts` + `.../[id]/route.ts`. Messages support one image attachment each (screenshots) — `POST .../[id]` takes `multipart/form-data`, not JSON. Files are saved to local disk (`src/lib/attachments.ts`, `uploads/messages/<threadId>/<uuid>.<ext>`, gitignored) — fine for a single-instance deploy, but swap for S3-compatible object storage before scaling to multiple instances or a container that doesn't persist disk across restarts. Attachments are served through an auth-gated route (`src/app/api/messages/attachments/[threadId]/[filename]/route.ts`, reuses `canAccessThread` from `src/lib/messaging.ts`) rather than `public/`, since screenshots are private to the order's participants.
- **Admin area** — `/admin/**`, gated twice: `middleware.ts` (coarse, Edge-safe, JWT role check) + `src/app/admin/layout.tsx` (DB-aware redirect for non-staff). `/admin/pricing` additionally requires `ADMIN` specifically (engineers can view orders/reply to messages but not edit pricing) — enforced both in the page and in the `/api/pricing/rates` routes.
- **Fab Capabilities page** — `/fab-capabilities` has no DB, but its *numbers* now come from `src/lib/fab-capabilities.ts`'s `FAB_CAPABILITIES` rather than a local literal, because the DFM engine checks against the same envelope and the two must not drift. Labels/formatting and the prose-only rows (tolerances, finish list, panelization support — nothing a rule can evaluate) stay in the page.
- **DFM checks** — `src/lib/dfm/` holds a pure, Tier-A ("no geometry engine") design-for-manufacturing engine: `run-dfm.ts`'s `runDfm(layers, context, rules)` returns a `DfmReport` of graded findings. Surfaced today as the CAM tool's **DFM Check** tab (`dfm-panel.tsx`); the PCB Order page is the next surface and needs no engine change, because `DfmLayerInput` is structurally satisfied by *both* `LayerEntry` (store) and `DetectedLayer` (`gerber-analysis.ts`) already. Thresholds are **not** global constants — they're user-editable `DfmTemplate` rows (PRIVATE per user, à la the address book; SHARED published by staff, à la blog/products), so `/api/dfm-templates` is publicly readable (the CAM tool works logged-out) while saving needs auth and SHARED writes are admin-only via `/api/admin/dfm-templates`. `rules` is a JSON blob (small, closed rule set — unlike `PricingRate`'s open-ended slabs) always revalidated through `parseDfmRules` (zod) on the way in. The seeded `isSystem` "ProEmbSys Standard" row is undeletable so a selectable template always exists. Full rationale + the unshipped Tier B/C phases: `DFM_DRC_ROADMAP.md`.
  - ⚠ **Adding a rule to `DfmRules` must use `.optional()` in the zod schema plus a default in `withRuleDefaults`.** Templates are already saved in the DB; a newly-*required* field fails validation for every one of them, and the non-throwing read path (`parseDfmRulesSafe`) then silently substitutes the baseline — wiping the customer's own thresholds. Optional-plus-default is a no-op for old rows.
  - ⚠ **All DFM measurement goes through `src/lib/dfm/measure.ts`, which converts via `parsedLayer.units`** — layer units are *not* guaranteed mm (the CAM store converts everything to a user-toggleable `targetUnit` that can be inches; `analyzeGerberSet` leaves native units; `parseExcellonDrill` returns mm). Never read a raw aperture/bounds number elsewhere. Regression test: run a check, flip the tool to inches, re-run — the report must be identical.
  - Checks are **advisory and never block an order**, and are only recomputed on an explicit "Run check" click, matching the existing convention that panel computation only happens on "Create Panel".
  - Two deliberate honesty constraints in the engine: macro apertures (KiCad `RoundRect` etc.) are excluded from feature-size measurement rather than guessed at, and smallest-pad is reported as `info` only since we publish no minimum-pad spec to grade against. Thin silkscreen is capped at `warning` (cosmetic, not unbuildable) — otherwise most real KiCad exports would show a hard error.
  - **Tier B (`dfm/holes.ts`)** — annular ring, unlanded holes, drill-to-drill web, holes outside the outline. Pairs each hole to its concentric pad by first recovering the drill↔copper translation with `recoverDrillOffset` (so it works whether or not "Align Drill to Board Center" was clicked); if no translation earns support it reports `info` rather than measuring against a mis-registered pad set. ⚠ **Plated vs non-plated matters**: NPTH mounting holes have no pad *by design*, so the unlanded check only judges holes known to be plated — read from `TF.FileFunction`/`TA.AperFunction` attributes in the drill file's raw text. Without this it fired on both real test boards.
  - **Tier C (`dfm/capsules.ts` + the worker's `checkCopperSpacing`)** — copper-to-copper clearance, computed from the tracespace **plot tree** (which `plot()` already builds and previously discarded) because macros are resolved there, unlike in our own parser. The whole grammar is flattened to one primitive — a *capsule* (segment + radius) — so clearance is one distance function; nets are grouped with union-find, and only different-net pairs are measured. Runs in the worker (a populated layer is ~20k primitives, ~500ms). Two corrections that real boards forced and that must not be undone: a **0.1 µm touch tolerance** (coordinate quantisation otherwise leaves shapes that should touch in different nets → 200 bogus "0.0000mm" violations), and **containment testing for filled regions** via even-odd ray casting (a pad flooded by its own pour never touches the outline → read as a separate net microns away). `minClearanceMm` is deliberately *not* a global minimum — the grid only compares pairs near the rule — so never present it as one.
- **Customer account** — `/account` (name + address book). `Address` supports multiple saved billing/delivery addresses per user with one default per type; `gstNumber` lives on the address (India ties GST registration to a specific place of business), not on `User`, since a customer can have several GST-registered billing addresses. Set-default is enforced by unsetting other addresses of the same type inside the same transaction, both on create and update (`src/app/api/account/addresses/route.ts` and `.../[id]/route.ts`) — never just flip the new one without clearing the old default, or you can end up with two.
- **Checkout addresses** — `PCBOrderPage` fetches the customer's saved addresses and auto-selects their defaults; a delivery address is required to place an order (not to save a quote), a billing address is optional (not every customer needs a GST invoice). Like `priceBreakdown`, the chosen addresses are snapshotted onto `Order.deliveryAddress`/`billingAddress` (`Json?`) at creation time rather than kept as live foreign keys — `Address` rows are user-editable and deletable, so a live FK would let a placed order's shipping details silently change or break later. `src/lib/format-address.ts` narrows the stored `Json` back into a typed shape for display on the order detail pages.
- **Uploaded Gerber files** — the browser previously parsed the uploaded `.gbr`/`.zip`/`.rar` client-side (for dimension/layer detection) and discarded it, sending only the filename string. `POST /api/orders` now takes `multipart/form-data` and actually persists the file via `src/lib/order-files.ts` (same local-disk pattern as `src/lib/attachments.ts`, but validated by extension rather than MIME type — browsers don't reliably report one for `.gbr`/`.rar` — and with no per-order subfolder, since the order doesn't exist yet at upload time). Placing a real order (not saving a quote) now requires a file, checked both client-side (`PCBOrderPage`) and server-side. Download is auth-gated at `/api/orders/[id]/file` (owner or staff only), same ownership check as `/api/orders/[id]`.
- **Staff management** — `/admin/team` (ADMIN only). `User.isActive` gates login in `src/lib/auth.ts`'s `authorize()` — deactivating a staff account (`DELETE /api/admin/staff/[id]`, despite the verb, only flips `isActive: false`) is deliberately **not** a hard delete: `Message.authorId` cascades on delete, and an Engineer's sent messages live in threads shared with customers, so hard-deleting would erase their side of past conversations. An admin can't deactivate or demote their own account (checked server-side in `.../staff/[id]/route.ts`, not just hidden in the UI). New accounts get a random temp password (works immediately, shown once in the creating admin's browser) plus a best-effort welcome email with a password-set link reusing the existing reset-password flow — email failure never blocks account creation.
- **Resend failures don't throw by default** — the Resend SDK resolves `{ data, error }` on API-level failures (e.g. a placeholder `RESEND_API_KEY`) rather than throwing; only network-level failures throw. `src/lib/email.ts` explicitly checks `result.error` and throws, so callers that branch on success/failure (like the staff-creation `emailSent` flag) aren't silently wrong. Because of this, `forgot-password`'s route wraps the send in `try/catch` — the reset token must still be created even if the email fails, matching the documented "always return 200" behavior.
- **Blog, Shop products, Testimonials** — all three follow the same shape: a Prisma model with `isActive`/`published` + `sortOrder`, an admin CRUD API gated to ADMIN or ENGINEER (`/api/admin/blog`, `/api/admin/products`, `/api/admin/testimonials`, plus `[id]` routes), a public read-only API returning only active/published rows (`/api/blog`, `/api/products`, `/api/testimonials`), and an admin page + client table component under `src/app/admin/**` / `src/components/admin/**`. Blog content is Markdown, rendered via `react-markdown` on the real `/blog/[slug]` route (outside the switcher shell, like `/fab-capabilities`) — arbitrary Tailwind descendant selectors (`[&_h1]:...`) style the output since `@tailwindcss/typography` isn't installed. `BlogPage`, `ShopPage`, and `HomePage`'s teaser sections all fetch from the public APIs client-side instead of the hardcoded `BLOG_POSTS`/`PRODUCTS` arrays that used to live in `portal-main.tsx` (removed).
- **Reorder** — the "Reorder this board" button on `/orders/[id]` (only shown to the order's own customer, not staff viewing via that same route) links to `/?page=order&reorder=<orderId>`. `PCBOrderPage` reads that param client-side, fetches the old order via the existing (already ownership-checked) `GET /api/orders/[id]`, and pre-fills every spec field from it — including re-fetching its stored Gerber file through the auth-gated download route and re-constructing a `File` object client-side so it runs through the exact same `handleFile()` analysis path as a fresh upload. Nothing about this is a special "confirm and repeat" flow — it lands the customer back at step 2 with everything pre-filled but fully editable (color, dimensions, delivery format, the file itself, all of it), then goes through the completely normal place-order flow, including a brand new server-side price recompute and its own independently-stored copy of the Gerber file.

### The switcher shell outside real routes

`Navbar` (in `portal-main.tsx`) is exported and reused directly by the standalone routes (`/fab-capabilities`, `/orders`, `/orders/[id]`, `/account`) that sit outside the client-side switcher — it accepts optional `page`/`setPage`; when omitted (standalone usage) it navigates to `/?page=<key>` instead of calling `setPage`. `App`'s `setPage` mirrors every section switch into the URL via `history.pushState` and a `popstate` listener re-reads `?page=` — so back/forward buttons, bookmarks, and middle-click all work even though sections aren't real routes. This is still deliberately not `useSearchParams()` + Suspense (avoids a second SSR-bailout mechanism); the URL read happens client-side only, mirroring the sidebar-width hydration pattern. Nav items render as real `<a href="/?page=…">` anchors with intercepted left-clicks. `Navbar` collapses to a hamburger drawer below 920px (`useIsMobile` hook in `portal-main.tsx`); the shell's layout is otherwise fluid via `clamp()` and `auto-fit` grids since inline styles can't use media queries. The shop cart state lives in `App` (single source — the navbar badge and `ShopPage` mini-cart both read it); there is no online checkout yet, the mini-cart's CTA is a prefilled order-enquiry `mailto:`.

### Gotchas worth knowing before touching auth/backend code

- Auth.js v5's `Session`/`JWT`/`User` type augmentation must target `@auth/core/types` / `@auth/core/jwt`, **not** `next-auth`/`next-auth/jwt` — the latter re-export from `@auth/core` but module augmentation doesn't follow re-exports, so augmenting the wrong specifier silently does nothing. See `src/types/next-auth.d.ts`.
- `src/lib/email.ts` constructs the Resend client lazily inside the function, not at module scope — constructing it eagerly throws if `RESEND_API_KEY` is unset, which breaks `next build`'s route-data collection (every API route module gets imported during that step, even ones never called).
- Any page using `useSearchParams()` needs a `<Suspense>` boundary or the production build fails (`login`, `reset-password`).
- Prisma `Decimal` fields (money) must be converted via `Number(...)` at the read boundary before use in the pricing engine or before passing to a Client Component — Decimal is a class instance and isn't a plain serializable prop.

### Tracespace patch + board-view substrate

`patches/@tracespace+plotter+*.patch` (applied by `postinstall` via patch-package) fixes an upstream bug in macro primitive 20 ("vector line"): the width offset was applied *along* the line instead of perpendicular, collapsing the side slabs of KiCad `RoundRect` pad macros into zero-area slivers (pads rendered as a "butterfly" — center box + corner circles, no sides). Don't delete the patch or reinstall without `postinstall` running.

The viewer's Board view composites per-layer worker SVGs itself (not `@tracespace/core` renderBoard). Its FR4 substrate is a bounds rectangle **clipped to the traced board outline** when `BoardView.shapePathD` is set (`gerberRenderBoardView` in `gerber-svg.ts` traces the outline layer via core's `boardShape` and rejects untrustworthy shapes — e.g. Protel Mechanical-1 dimension ticks that close into degenerate slivers — falling back to the plain rectangle). KiCad exports *filled* silkscreen shapes as dense 0.04mm hatch strokes; a solid silk disc on screen is usually real design content, not a rendering bug.

The same degenerate-outline case also breaks the `viewBox` tracespace's own `renderBoard()` computes (a near-zero-area box, since it derives directly from that same untrustworthy traced shape) — so `gerberRenderBoardView` no longer takes `board.top.properties.viewBox` unconditionally. It first unions every layer's own plotted bounds (Gerber-native Y-up mm, from `plotResult.plotTreesById`); when the outline-trust check fails, it uses that union (converted to Y-down screen-space: `x=minX, y=-maxY, width, height`) as the viewBox instead of tracespace's degenerate one. Trusted-outline files are unaffected — they still use tracespace's own viewBox.

**tracespace's board compositor is unit-naive** — `coreRenderLayers`/`coreRenderBoard` merge all layers into one shared coordinate space using each plot tree's raw native numbers, never converting between inch- and mm-native layers (it stamps the same union viewBox on every per-layer SVG, only the `width`/`height` unit *suffix* differs). A homogeneous file set is self-consistent by luck; a mixed set misaligns by 25.4× — and our own Excellon pipeline *creates* mixed sets from consistent ones, since `serializeParsedDrillToExcellon`/`generateNormalizedExcellon` always emit METRIC (drill auto-detect, format override, and "Align Drill to Board Center" all re-serialize the drill in mm while inch-native Gerbers stay untouched). Symptom: board artwork collapses into a corner of a huge wrongly-sized substrate. Fix: `scalePlotTreeToMm`/`scaleBoardShapeToMm` in `gerber-preprocess.ts` scale every inch-native plot tree (and the boardShape, iff the outline layer's tree was inch-native — a BoardShape doesn't carry units of its own) to mm in place, immediately after `corePlot` and before any render step, so the whole downstream pipeline shares one mm space. The plot-tree grammar is closed (`@tracespace/plotter`'s `tree.d.ts`), so the walk is exhaustive; arc `theta` values are angles and are not scaled. `BoardView.shapeScale` is consequently always `1` now (the clip path d is already mm).

`src/lib/gerber-preprocess.ts`'s `normalizeGerberMacroPrimitives()` runs before every `@tracespace/parser` call — the worker render path, the main-thread board-view duplicate in `gerber-svg.ts`, and `src/lib/board-contour.ts`'s `traceBoardContour` (routing's contour tracer, four call sites in total as of the contour-routing feature) — to work around a tracespace bug: it silently drops an aperture macro's geometry when a primitive's point list is wrapped across multiple lines before the terminating `*` — valid RS-274X (Proteus does this routinely), but tracespace's tokenizer treats the embedded newline as ending the primitive early, so every flash of that D-code renders as nothing (confirmed to break both copper and soldermask on real exports). The fix collapses newlines strictly inside `%AM...%` blocks; it's a no-op for the far more common single-line-primitive macros (e.g. KiCad's multi-primitive-per-line `RoundRect`, verified byte-for-byte identical parse/render before and after).

### Coordinate system

The tracespace renderer emits **Y-down SVG coordinates** (Y=0 at top = Gerber maxY). The viewer works in this native SVG space. When displaying cursor position, gerberY = −screenY. The panelization engine works in **Gerber Y-up mm coordinates** (Y increases upward), and the exporter writes coordinates in that convention.

### Gerber output format

The `OutputFormat` struct controls the `%FS...%` header in exported files. Default is 4.6 mm absolute (handles boards up to 9999mm). `autoDetectIntegerDigits` in `panelization-engine.ts` adjusts the integer digit count if the panel is unusually large.

Panel-overlay apertures (L-shape marks, stroke text, donuts, fiducials) are allocated **dynamically above the customer's max D-code** (`findMaxDCode` in `panelization-engine.ts`, base ≥ 301 rounded to the next century) — never hardcode overlay D-codes like the old D53/D54/D200/D210; customer Gerbers routinely use those ranges and duplicate/conflicting `%ADD` definitions trip CAM tools.

### Panel legend text (region font)

Panel text (customer/PCB reference on the top rib, per-layer labels on the bottom rib) renders as **filled Gerber regions** (`textFont: 'region'`, the default) or single-stroke polylines (`'stroke'`), selected in `export-panel.tsx`. The region path (`region-font.ts`) extracts **real glyph outlines** from an embedded Geist Regular subset (`region-font-data.ts`, base64 OFL-1.1 font, ~12 KB, parsed once via opentype.js and memoized per glyph): outlines are normalized so cap height = 1.0, flattened to polylines (adaptive Bézier subdivision), and split into dark outer / clear counter contours by **nesting depth** (a contour inside an odd number of others is a hole). Emission is CAM350-style: all outer contours under `%LPD%` + G36/G37, then counters under `%LPC%`, then reset to `%LPD%`. `measureRegionText` is the **single source of region text metrics** — shared by the emitter, panel-label positioning (`generateLayerLabels`), and the preview, so all three stay aligned (never re-hardcode advance/char widths). The on-screen preview (`gerber-viewer.tsx`) is **WYSIWYG**: in region mode it draws the exact same laid-out polygons via `getRegionTextPolygons` (both call the shared `layoutTexts`), so preview and exported Gerber are byte-for-byte identical coordinates. Glyphs are flattened to line segments only (no G36 arcs) for universal CAM safety. To change the typeface, re-subset a permissive (OFL/Apache) TTF and regenerate `region-font-data.ts`. Rib text size is user-configurable per rib (`PanelConfig.topRibFontSize` / `bottomRibFontSize`, both default 2.8mm cap height) via number inputs in `export-panel.tsx`, next to the font-type selector — `generatePanelMetaText` and `generateLayerLabels` read these instead of a hardcoded constant. `parseExcellonDrill` (in `gerber-parser.ts`) handles Altium 9+-digit coordinates (5.5 autodetect), Allegro `;Holesize`/`;FILE_FORMAT` comment headers, `M00` tool changes, stepped `R` repeat commands, headerless files (no `M48`/`%`), and explicit-decimal coordinates (KiCad) — ported/adapted from the standalone `pcb-panelization-tool` repo's `font-fix` branch, which is the upstream lineage of this tool.

⚠ **Some Allegro/PentaLogix-ViewMaster exports carry `;Holesize`  comments (units) but never a `;FILE_FORMAT` comment (digit width)** — leaving the default 2.4 split to truncate the file's actual 8-digit fixed-width coordinates down to their last 6 digits, silently moving every hole and producing negative bounds on a board with none. Confirmed on a real customer file pair: the digit truncation was only caught by cross-checking the drill's implied board footprint against the companion `.rou` file's own `;EXTENTS:` comment (in mils), which gave a clean 152.4mm square that only a 3.5mm split lands inside. Detected up-front (same pattern as the Altium 9+-digit check right above it in the source): a `;Holesize N. = ... MM` comment plus consistently 8-digit coordinates with no format ever declared assumes 3.5 metric.

### Drill zero suppression — two opposite conventions

`DrillZeroSuppressionMode` in `gerber-parser.ts` names **which zeros were removed from the file** (`'leading'` → pad left to restore). `DrillZeroSuppression` in `panelization-engine.ts` is the *export* setting and is deliberately **inverted**, because CAM350 reads the LZ/TZ header keywords backwards: exporting `'leading'` strips *trailing* zeros. They don't collide (exports carry an explicit header; the drill handed to the viewer is normalized to explicit decimals) — but never unify them without re-testing in CAM350. `'none'` means fixed-width coordinates in both.

A drill layer keeps its pristine upload in `LayerEntry.originalContent`; `rawContent` is the *normalized* Excellon (explicit decimals) consumed by the exporter and the SVG renderer. Drill format overrides and `autoDetectDrillFormat` must always re-parse from `originalContent` — re-parsing `rawContent` is a silent no-op, since explicit decimals ignore the format entirely.

**Export drill format defaults to match the upload.** `PanelConfig.drillFormat` used to always start at the hardcoded `DEFAULT_DRILL_FORMAT` (Excellon 2:4 inch) regardless of what the customer actually uploaded. `store.ts`'s `maybeSyncExportDrillFormat` now auto-populates it from the first drill layer's resolved `DrillMeta` on import (`addLayer`/`addLayersFromZip`/`addLayersFromRar`), converting through the leading/trailing inversion documented above. It only fires while the config is still `sameDrillFormat` to `DEFAULT_DRILL_FORMAT` — once the user picks anything in the Drill & Marks tab (or a prior auto-sync already changed it), later drill imports leave it alone. Comparison is structural (ignores `preset`, which is just a UI label), and the detected format gets tagged with a matching preset name only if it exactly equals one of `DRILL_FORMAT_PRESETS`, else `'custom'`.

`parseExcellonDrill` converts *everything* to mm before returning — coordinates during body parsing, and tool/aperture diameters in a final pass (the layer declares `units: 'mm'`, so `convertLayerUnits` no-ops on it; anything left in file units at return survives forever). The diameter pass must stay AFTER the zero-suppression plausibility block, which deliberately works on raw-unit widths with its own scale factor. Skipping aperture conversion was a real bug: `serializeParsedDrillToExcellon` (used by drill align and rotate) wrote inch diameters under its METRIC header — `T01C0.0240` — rendering every hole as a 25.4×-too-small uniform dot.

"Align Drill to Board Center" (`store.ts:alignDrillLayersToBoard`) recovers the drill↔Gerber origin offset **exactly** via `src/lib/drill-alignment.ts` (`recoverDrillOffset` — algorithm ported from the MIT-licensed delta-gerber project's `DrillGerberAlignment`): every plated hole is concentric with its copper pad, so the set of (pad − hole) vectors collapses onto a single translation; vote all hole×pad difference vectors on a 0.05mm grid, take the dominant bucket, refine to the mean exact offset, and accept only when ≥50% of holes (and ≥3) snap onto pads within 0.075mm. Verified 315/315 hole matches on a real Protel relative-origin export. When no translation earns enough support (e.g. an NPTH-only drill), it falls back to centering the drill bbox on the **copper layers'** combined bounds (not the whole-board union — silkscreen extending past the copper skews the center). Pad/hole centers must be collected with `resolvedFlashCenters`, which resolves modal coordinates — Protel flashes with a bare `D03*` whose position lives entirely on the preceding move, so a flash command's own `coordinate` can be empty.

`generateNormalizedExcellon` always converts coordinate *values* to mm, but must also rewrite the header's unit declaration to match — it previously only did so for bare `METRIC`/`INCH` tokens, silently leaving `M71`/`M72`-declared files with mm-valued coordinates under a stale inch-mode header (self-contradictory Excellon, mis-scaled in both the on-screen render and — since `rawContent` feeds the exporter too — the actual fabrication output). Unit-token detection now also matches `M71`/`M72`, and a final fallback at the `%` end-of-header marker declares `METRIC` if nothing upstream already did.

⚠ **A drill layer's on-screen render normally comes from the RAW upload, not our parsed representation** — `store.ts`'s initial `gerberToSvg()` call for a drill file passes `content` straight through to tracespace, which has its own, completely independent Excellon interpretation (parsing, format-guessing, all of it). Our `parseExcellonDrill` result only drives panelization math, DFM, bounds comparisons, etc. — normally this is fine because tracespace handles the same well-known conventions we do. But for a file whose format we only reached via a content-shape heuristic (`DrillMeta.formatGuessedFromContent` — the Altium 9+-digit and Allegro-Holesize-without-FILE_FORMAT cases above), tracespace has no idea about either heuristic and makes its own, uncoordinated guess at the same ambiguous digits — confirmed on the real Allegro-Holesize file: it has **no `Tnn` tool-select command anywhere in its body at all** (tool changes are implied purely positionally via bare `M00`), so tracespace's plotter — which needs an explicit tool selection to resolve a flash's diameter — silently dropped every single hole (0 plotted children) regardless of digit format. `store.ts`'s `drillSvgSourceContent()` checks that flag and, when set, feeds tracespace `serializeParsedDrillToExcellon(parsedLayer)` instead of the raw upload — a complete synthetic Excellon file (real `M48` tool table + a `Tnn` select before every tool change) built from our own already-correct parse, sidestepping tracespace's guess entirely rather than trying to coordinate with it. `generateNormalizedExcellon` doesn't work for this — it only rewrites the original text line-by-line and can't invent tool-select commands that were never there.

### Milling slots from incoming `.rou` files

`detectLayerType`/`isExcellonDrillFile` both treat an incoming `.rou` as ordinary drill data, but a real rout file (confirmed against a customer file exported alongside the Allegro-Holesize `.drl` above, for the same job) is plain G-code, not Excellon: `T01` selects a tool, `G00X..Y..` rapids to a start point, `G41`/`M15` begin a cut, a run of `G01X..Y..` traces the path, `M16` retracts. Feeding that to `parseExcellonDrill` (which reads any line containing `X`/`Y` as a hole position) turned every cut move into a spurious "drill hit" at the corner of the milled shape, with no diameter.

`src/lib/routing/import-rout.ts` recognizes and parses this dialect properly: `isRoutGcodeFile` discriminates it from genuine Excellon via a **bare tool select with no diameter anywhere** (`T01`, never `T01C<dia>`) alongside the plunge/retract + cutter-comp markers — genuine Excellon always pairs a tool select with a diameter declared somewhere. `parseRoutSlots` walks the G-code into one closed polygon per plunge/retract (`M15`...`M16`) block. Two things this deliberately does NOT do:
- **Recover a cutter-compensation offset.** The real file's `G41` (cutter comp left) suggested the coordinates might be a tool-center path needing a bit-radius correction like this repo's own routing engine applies — but the incoming file never declares tool `T01`'s diameter, so that correction isn't computable from the file alone. Confirmed instead against the board's own `SLOT HOLE REPORT.XLS` (exact `SLOT_SIZE_MAJOR/MINOR`/`SLOT_X/Y`): the raw G01 coordinates already trace the *finished* slot boundary with zero cutter offset needed, so rendering them verbatim is the honest, correct answer — not a shortcut.
- **Auto-detect the coordinate digit format.** Confirmed to use the identical fixed 8-digit-no-suppression convention as its companion `.drl` (3 integer + 5 decimal digits, mm) — a real, tool-specific convention, not guessed per-file.

`routSlotsToGerber` renders each polygon as a filled Gerber region (`G36`/`G37`, dark polarity, **explicit-decimal coordinates** — tracespace accepts these directly in Gerber body content, sidestepping the whole fixed-width/zero-suppression class of bug for the *output* side even though the *input* dialect needed the fixed-width decode above). `store.ts`'s `parseDrillOrRoutContent` runs `isRoutGcodeFile` **before** `isExcellonDrillFile` (a rout file's body also satisfies the Excellon heuristics — `M30`, `G90`, real coordinates), converts to this synthetic Gerber text, and classifies the resulting layer as `type: 'drill'` — deliberately not a new `LayerType` member (see the routing roadmap's documented reason to avoid that), and 'drill' already correctly participates in Board-view compositing. Rout-derived layers are recognizable by `!parsedLayer.drillMeta` (only `parseExcellonDrill` ever sets that field) and must be excluded from the drill size-mismatch auto-detect in all three import paths — their bounds are a handful of small milled slots, not the whole board, and running `autoDetectDrillFormat` on G-code text that was never Excellon would corrupt an already-correct result.

### Excellon G85 slots (drilled/milled slots declared in the drill file itself)

Distinct from `.rou`-imported slots above (a whole separate router G-code file) — this is a slot declared *inside* an Excellon drill file via the standard `G85` canned slot cycle: `X<start>Y<start>G85X<end>Y<end>` mills between two points at the current tool's diameter. `parseExcellonDrill` had zero awareness of this: the generic coordinate-hit regex only captures the digits immediately after each axis letter, so a G85 line silently kept just the start X/Y and dropped everything from `G85` onward — turning a slot into a round hole at the wrong (start-only) position, with no warning. The G85 pattern is now matched **before** the generic coordinate-hit check (which would otherwise partially consume the line).

Slots are tracked in a new `GerberLayer.drillSlots?: DrillSlot[]` field (`{ start, end, toolCode, diameterMm }`), deliberately **kept out of `commands`** — every existing consumer that walks `commands` looking for `type === 'flash'` (hole counting, drill-alignment pad matching, DFM unlanded-hole checks, the panelized-drill-file/G-code hole collectors) means "a single drilled point with a matching copper pad"; folding a two-point slot into that stream would silently corrupt all of them rather than just being ignored by the ones that don't care about slots yet. The tradeoff: every one of those consumers that legitimately *does* need to know about slots has to be updated by hand, not "for free" — done so far for:
- **Bounds** (`expandBoundsForSlots`, shared helper) — folded into `parseExcellonDrill`'s own bounds calc and into `convertLayerUnits`' recalculation, or a board whose only geometry is a slot panelizes with a bounding box too small to contain it.
- **Unit conversion** (`convertLayerUnits`) — converts slot coordinates and diameter too (normally a no-op for drill layers, which are always parsed straight to mm, but must stay correct regardless).
- **Drill align** (`alignDrillLayersToBoard` in `store.ts`) — shifts slot start/end by the same recovered offset as every hole, or a slot would stay at its pre-alignment position while the holes around it moved, throwing the two out of registration.
- **Serialization** (`serializeParsedDrillToExcellon`) — emits a `G85` line per slot after the flash loop, or drill align/rotate would silently drop slots from the regenerated file (including the on-screen re-render, which re-renders from this serialized text).
- **Panelized Excellon export** (`generatePanelizedDrill` in `gerber-exporter.ts`) — a separate pass alongside the existing flash loop, translating *both* endpoints by each panel position; without this the exported customer drill file would silently lose slot data on every panelized order.
- **G-code** (`generateDrillGcode`/`generateGcodeFiles` in `routing/gcode.ts`, via a new `collectPanelizedDrillSlots` mirroring `collectPanelizedDrillHoles`) — see below.

**Not yet updated** (no current caller needs it, but a future one might silently under-count): DFM hole/annular-ring checks, drill hole counting in the Layers panel, `resolvedFlashCenters`-based pad matching. None of these are wrong today — they just don't know slots exist, same as before this feature — but "slots are invisible to X" is the right mental model, not "slots are handled everywhere."

`generateNormalizedExcellon` (format normalization) needed **no changes** — it rewrites raw text with a generic global `X`/`Y`-token regex, not command reconstruction, so it already preserves the literal `G85` text between the two coordinate rewrites on a slot line. Confirmed by direct test rather than assumed, since every other function touching drill data in this file needed a fix.

**G-code for slots**: a slot's tool diameter *is* the slot width (no separate cutter-offset math the way the depaneling router needs — the bit just traces the slot's own centerline). `generateDrillGcode` appends each slot after its diameter's point holes as plunge → lateral cut → retract (vs. plunge → retract for a point), sharing that tool's file rather than getting its own — matching the shop's existing "one program per bit" convention the round-hole grouping already follows. No real G85 sample file exists to match a machine's exact convention against (unlike every other G-code template in this file, which are byte-verified against real production files), so the lateral move's feed reuses `ctx.routeXYFeedMmPerMin` — the existing XY cutting feed already in this same context for the router — rather than inventing a new field; this is a reasoned default, not a confirmed-against-real-hardware convention. The `#<XY_Feed>` header line and the slot block are only emitted when the file actually has slots, so every pre-existing pure-hole file stays byte-identical (verified).

### Viewer preview features (hover-isolate, soldermask color)

Hovering a layer row in the Layers panel sets `store.hoveredLayerId`; `gerber-viewer.tsx`'s `visibleLayers` memo isolates to just that layer while `viewMode === 'layers'` (Individual layers overlay), ignoring each layer's own visibility toggle, and reverts to the normal filtered/z-sorted list on mouse-leave. Scoped to Layers mode only — Board mode is a single composited render (via per-layer SVG compositing, not tracespace/core's `renderBoard`) and isolating one layer there would need a much bigger re-compositing change.

The Board view's soldermask color (Green/Red/Blue/Purple/Yellow/Black/White, `store.boardColor`, default Green) is purely cosmetic — it never touches exported Gerbers. Swatches sit in the top-left toolbar, visible only in Board mode. `board-colors.ts` supplies two shades per color: `substrate` (bare FR4 field) and `copperTint` (copper as seen through the mask) — both feed the shared `getPcbColor()` compositing helper (replacing the old hardcoded `#113f1d`/`#2e9e4f` green). Pad-finish gold (`#d4af37`) stays constant across every color, matching real boards where ENIG/HASL finish is independent of soldermask color. Silkscreen is normally light gray (`#e8e8e8`) but flips to black (`#1a1a1a`) via `silkColorFor()` when the color is White, since white ink on a white mask would be invisible — real white-soldermask boards are silkscreened black for the same reason. This is a distinct, purely-visual palette from `src/lib/solder-mask-colors.ts` (a flat single-color swatch used by the PCB Order flow's spec picker) — don't conflate the two or try to unify them; one is a fabrication spec option, the other is a preview-rendering approximation with an extra "Purple" not offered as an order spec.

**Oversized mask openings (fiducials) and `getMaskClipPairs`.** A soldermask opening is routinely larger than the copper pad beneath it — most visibly on fiducials, which need clearance past the copper dot for optical recognition (e.g. a real KiCad export: a 1.5mm copper fiducial pad under a 3.0mm mask opening, D18 vs D20). The board compositor renders each layer as its own worker SVG fragment tinted by `currentColor` — it has no idea a "mask" fragment's geometry is a *negative-polarity opening*, not paintable ink, so naively filling it flat opaque gold (the old behavior) painted the entire oversized opening gold, hiding the ring of bare FR4 substrate around the pad that other viewers (tracespace.io, delta-gerber) correctly show — this read as "fiducial missing/wrong" even though the source Gerbers were fine (`WLC_Indicator` fiducial FID2 confirmed this: D18 1.5mm copper pad, D20 3.0mm mask opening, `TF.FilePolarity,Negative` on the mask file). Fix: `getMaskClipPairs()` (`board-colors.ts`) pairs each mask layer with its same-side copper layer; the mask layer is never painted directly — its geometry is used only as an SVG `<mask>` (via `RawSvgMask` in `raw-svg-group.tsx`, forced to paint white regardless of the layer's real display color) applied to a second, gold-colored copy of the matching copper layer. Gold then only appears where copper actually exists; the substrate shows through everywhere else in the opening, matching reality. When mask opening ≈ copper size (the overwhelming majority of ordinary SMD pads), the mask has no visible effect and rendering is unchanged. Implemented in all three board-compositing call sites that exist for this reason (single-PCB Board view and the panelized `<use>`/`<defs>` Board view in `gerber-viewer.tsx`, plus `board-preview.tsx`) — a layer without a same-side copper partner falls back to the old flat-paint behavior unchanged.

This originally used an SVG `<clipPath>` instead of `<mask>` — reverted after it broke on the very file that motivated the fix. A real board's mask layer can carry 1000+ shapes (one opening per pad), and past a few hundred children this renderer's `<clipPath>` silently resolves to an *empty* clip region — reproducible from a fresh page load, not a mutation-invalidation artifact — while the exact same geometry works fine as a `<mask>` (confirmed by swapping just that primitive against the live `WLC_Indicator` fiducial and sampling the composited pixel color). `<mask>` is luminance/raster-based rather than vector path intersection and doesn't hit the same wall at this scale. Don't switch this back to `<clipPath>` without re-verifying against a real multi-hundred-pad board, not just a synthetic single-shape test — that's exactly the gap that let the original regression ship.

⚠ **A mask opening with NO copper anywhere beneath it was still fully invisible** even after the fix above — confirmed on a real customer board: `FV30359-1_NC_MSK-TOP.art` has an 18.3mm circular soldermask opening (D27) centered on each of two large inductor footprints (L1/L2), with zero copper geometry underneath on either the top or bottom copper layer (a keepout/relief area, not a pad). `getMaskClipPairs`'s technique only ever reveals gold *copper* through a mask opening — with no copper to reveal, nothing paints, and the opening reads as plain board background, exactly like a spot with no mask feature at all. This is the same underlying case as the fiducial annulus above (bare FR4 within a mask opening, no copper at that specific point) — just with *zero* copper anywhere in the opening instead of a smaller copper dot in the middle. Fix: `EXPOSED_SUBSTRATE_COLOR` (`board-colors.ts`) — a single tan/fiberglass tone, deliberately constant across every soldermask color choice, since bare FR4 looks the same regardless of what color mask the rest of the board uses. Painted as a rect clipped by the same mask, *underneath* the existing gold-copper reveal, at all three board-compositing call sites — so it shows through wherever the opening has no copper (both the fiducial annulus and a fully copper-less opening like this one), and is invisible wherever the gold-copper layer paints over it opaque. This is a visible change to the previously-shipped fiducial look (the annulus now reads as this tan tone instead of the board's own dark `substrate` background) — deliberately, since both are physically the same bare-FR4 phenomenon and the tan tone is the more accurate one of the two.

⚠ **`nativeSvgBounds` (the `bounds` used for the exposed-substrate rect above, and for `bgRect`) is already in native SVG Y-down space — do not negate it.** The exposed-substrate rect's first implementation used `y={-bounds.maxY}` (treating `bounds` as Gerber Y-up and converting), which put the rect roughly one board-height off from where it should be — it only covered the bottom portion of the board, so a feature in the upper half (like the L1/L2 example above) got no coverage at all and looked exactly as unfixed as before. Caught by pixel-sampling the live render (not just eyeballing a screenshot) and confirmed against the already-correct sibling code right above it, which uses `y={bounds.minY - 0.2}` with no negation. `bgRect`'s own construction is the reference for this convention — match it exactly rather than re-deriving the sign from the Gerber-Y-up/SVG-Y-down convention described earlier in this file, which applies to *raw Gerber coordinates*, not to `bounds` values already handed to you in SVG space.

### PCB Order page board preview (`board-preview.tsx`)

`PCBOrderPage` (in `portal-main.tsx`) renders a read-only composited board preview after a Gerber upload, in the soldermask color the customer picked from the existing **Color** spec buttons — the spec picker drives the preview directly (`specs.color` passed straight in as `maskColor`), there's no separate preview-only color control. Deliberately **store-independent**: `PCBOrderPage` never touches the Panelization tool's Zustand store, so `board-preview.tsx` classifies and renders layers itself from the same raw `{name, content}[]` entries `handleFile` already extracts for `analyzeGerberSet` (lifted into `previewEntries` state so the ZIP isn't parsed twice). Classification mirrors `store.ts`'s exact 3-tier priority — content-sniffed drill files first, then the file's own `TF.FileFunction` attribute (via `gerberToSvg`'s `layerAnalysis`, which requires rendering *before* classifying), then `detectLayerType`/`detectLayerSide` filename heuristics as a last resort. The TF.FileFunction tier isn't optional: plenty of real exports (e.g. this project's own `SenseBus_TH_Pro-B_Mask.gbr` test fixture) don't match the filename heuristic's expected patterns even though the file correctly declares its function — skipping straight to filename-only classification silently drops those layers as `'other'`. Shares `RawSvgGroup` (`raw-svg-group.tsx`) and the color/opacity/z-order tables in `board-colors.ts` with `gerber-viewer.tsx` so the two renders can't drift apart; a version-bump to either file should be re-verified in both places. Static + fit-to-view with a Top/Bottom toggle (no pan/zoom, unlike the CAM tool's viewer) — an intentionally lighter-weight preview for the order page.

### Fiducial placement must avoid rib text, not just holes

`computePanel`'s fiducial placement (`fid_bl`/`fid_br`/`fid_tr`) originally validated a candidate position (`isValidPosition`) against panel bounds, the PCB grid, tooling/reference holes, and other fiducials — but never against the rib text drawn on top of the same ribs. On a real board this collided in practice: `fid_br`'s primary candidate (`panelWidth - sideRibRight - 40`) landed exactly inside the bottom-rib per-layer label text (e.g. "Bottom Copper", right-anchored near `panelWidth - 17`), confirmed via live DOM measurement — the candidate X and the label's real rendered left edge matched to sub-mm precision.

Fixed by reserving two rib-text zones before validating fiducial candidates: `generatePanelMetaText()` (then still named `generateTopRibText`) is called *before* fiducial placement (it only needs `info` + `toolingHoles`, both already available) so the **real measured** customer/PCB-name text extent on the top rib can be reserved exactly via `measureRegionText`. The bottom rib's per-layer labels aren't knowable this early — `computePanel` has no access to the customer's actual layer list — so a **worst-case** zone is reserved instead, sized from `measureRegionText('Bottom Copper')` (the longest label string this codebase's naming ever produces), unioned across both the top-anchor and bottom-anchor label positions `generateLayerLabels` uses. `collidesWithRibText(x, y)` checks both zones and is wired in as a new condition inside `isValidPosition`. This doesn't invent a new fiducial position — it makes the *existing* per-corner candidate-fallback mechanism (each corner already tries a secondary candidate on a different rib if the primary is rejected) correctly reject the colliding primary candidate so the already-clear fallback takes over.

### Layer-ID text must avoid tooling/reference holes — the reverse of the fiducial fix

`generateLayerLabels`'s TOP-anchored labels (`topFirstCharX = panelWidth - 30`, growing rightward) and BOTTOM-anchored mirrored labels (`bottomFirstCharX = panelWidth - 17`, growing leftward) were two hardcoded "mm from right border" offsets, tuned against nothing in particular — meanwhile the tooling/reference hole block earlier in `computePanel` places `tooling_br`/`ref_br` independently, and on the *default* config (5mm ribs, default insets) they land at ~97.5mm/102mm on a 110mm panel. Confirmed via live DOM measurement: the default "Top Copper" label rendered at x=80.05–101.03, directly swallowing `tooling_br` (96.5–98.5) whole — a tooling/reference hole would drill straight through the printed layer-ID text, not a near miss. `generateLayerLabels` even already received a `toolingHoles` parameter for this — it was just never read (visible as the pre-existing `'toolingHoles' is defined but never used` ESLint warning).

Fixed the opposite way from the fiducial case: holes are fixed geometry by the time this function runs, and this is the *first* place the real label strings (and hence real `measureRegionText`-measured widths) exist — `computePanel` itself has no layer list to consult. `clearHolesGrowingRight`/`clearHolesGrowingLeft` take the widest label per group (topLabels grow right, so are checked/shifted left to clear; bottomLabels grow left, so are checked/shifted right to clear) against every hole on the bottom rib (`toolingHoles` filtered to `y` within `[0, sideRibBottom]`), iterating to a fixed point since clearing one hole can newly overlap another further along — bounded by `holes.length + 1` passes, same convergence-bound style as the fiducial candidate fallback. Verified on the reproducing panel: "Top Copper" moved to x=74.35–95.33, clearing `tooling_br` (96.5–98.5) by >1mm; also verified against a pathological worst case (the `l.name.toUpperCase()` fallback path for `'other'`-type layers, which can produce arbitrarily long strings) — the anchor correctly walks left as far as needed rather than silently overlapping.

### Panel meta text (revision, date, PCB size, panel size) — tiered rib placement, `generatePanelMetaText`

The rib text used to carry only the customer/PCB-name line — `PanelInfo.revision` and `.date` were already captured (editable in `export-panel.tsx`, used in filenames and the exported README) but never actually rendered onto the panel, and PCB/panel dimensions weren't rendered at all. `generateTopRibText` (single hardcoded line) was replaced by `generatePanelMetaText`, which builds four candidate lines — name (always kept), `Rev {revision}  {date}`, `PCB {w}x{h}mm`, `Panel {w}x{h}mm` — and places as many as fit, most important first, across three tiers, each only used once the previous one runs out of room:

1. **TOP rib**, stacked below the name line at the same anchor — as many lines as `config.sideRibTop` has height for (`Math.floor((sideRibTop - margin) / (fontSize * 1.4))`).
2. **BOTTOM rib, LEFT side** — the right side is `generateLayerLabels`'s territory, so overflow lines go on the left, clear of `ref_bl`/`tooling_bl` and of the worst-case per-layer-label zone (`worstCaseBottomRibLabelZone`, extracted from the fiducial fix above and shared so the two reservations can't drift).
3. **LEFT/RIGHT side ribs, vertical text** (rotation 90°, reads bottom-to-top) — only entered if the user has actually given the panel side ribs (`sideRibLeft > 0 && sideRibRight > 0`), split between the two ribs, centered on the grid's own vertical span.

Anything that still doesn't fit is dropped with a `console.warn`, never silently overlapped — this is cosmetic branding text, not a fabrication safety feature (contrast with the routing/DFM engines, which raise a blocking error instead).

**`clearHolesAlongAxis` must try both directions, not just retreat.** The layer-label hole-avoidance fix above (`clearHolesGrowingRight`/`Left`) only ever retreated — shifted the anchor backward until clear of a hole — which was fine there (that anchor starts near the panel's *right* edge with open space to its left) but is wrong for text anchored near an edge with a hole close by on the *growth* side: retreating from a small hole a few mm to the right of a left-edge anchor pushes the anchor negative, off the panel entirely — confirmed live (the bottom-rib-left revision/date line landed at x=−32mm on a 110mm panel before this fix). The two local functions were promoted to one shared `clearHolesAlongAxis(startX, width, holes, direction, clearanceMm)` that, on each collision, computes both options — retreat behind the hole's near edge, or advance past its far edge — and picks whichever needs less displacement from the current anchor. Verified this doesn't change the earlier layer-label fix's result (retreat is still cheaper there) while fixing the bottom-rib case (advance is cheaper — the text now lands a few mm to the right, on-panel).

**The fiducial reservation zone had to grow with it.** `fid_bl`'s default candidate sits at `sideRibLeft + 15`, close enough to the new bottom-rib-left overflow text that once that text could legally *advance* past the tooling/reference holes, `fid_bl` started landing on top of it — the bottom-rib collision check in the fiducial block only ever reserved the (hardcoded, worst-case) *right*-side per-layer-label zone, never the real text now living on the left. Fixed by unioning that reservation with the real measured span of any `infoTexts` entry tagged `location: 'bottom-rib'`, mirroring how the top-rib reservation already scans `infoTexts` for `'top-rib'` entries.

**A latent bug in the top-left-tooling-hole lookup surfaced during testing** (unrelated to the placement logic above, but in the same code path): `toolingHoles.filter(h => h.type === 'tooling').reduce(fn, toolingHoles[0])` seeds the reduce from the *unfiltered* array's first element — if no `'tooling'`-type hole exists at all (small ribs can make `addHole`'s edge-distance check reject every tooling hole while the smaller reference holes still fit), the filtered array is empty and `.reduce()` silently returns that unfiltered seed, which can be a `'reference'`-type hole. Fixed by seeding from the *filtered* array's own `[0]` instead.

**Side-rib vertical text reuses the existing `location: 'left-rib' | 'right-rib'` + rotation machinery** — both `gerber-viewer.tsx` (preview color) and `region-font.ts`'s `layoutTexts` (rotation math, used by both the preview and the Gerber emitter) already handled arbitrary rotation and this location tag generically; only the producer side (`generatePanelMetaText`) was new. For a `mirrored: true` copy at rotation 90°, the anchor must be the *end* of the intended vertical span (`startY + textLen`), not the same start point the normal copy uses — mirroring flips the reading direction (`nx = -nx` in `transformPoint`), so anchoring both copies at the same point would make them cover different, non-overlapping spans instead of the same footprint (the existing horizontal top-rib code already does the analogous thing via a separate `rightAnchorX` for its mirrored copy).

Known accepted limitation: on a panel too small even for the *original* single name line (e.g. a 20×20mm single PCB with the default rib and font sizes), text can still run off-panel — there is fundamentally no on-panel position for a ~50mm-wide string on a 30mm-wide panel, and no placement algorithm changes that. Not attempted here; affects the pre-existing name/layer-label text equally, not something this change introduced.

### Fiducials must guarantee "minimum 3" regardless of which ribs exist

Each corner (`fid_bl`/`fid_br`/`fid_tr`) only ever had two fixed candidates — a primary on the bottom/top rib, and a fallback that centers the fiducial *inside* the left/right side rib. Removing the left AND right side ribs (`sideRibLeft`/`sideRibRight` set to 0) broke this structurally: the fallback candidate for `fid_bl`/`fid_br` (`sideRibLeft/2` / `panelWidth - sideRibRight/2`) sits exactly on the panel edge once that rib's width is 0 — outside the margin check — so it can never succeed. Confirmed live: only `fid_tr` survived (its primary candidate happens to live on the TOP rib, which was still present); `fid_bl`/`fid_br` silently vanished, leaving 1 fiducial instead of the required 3.

Fixed with a proper scanning fallback (`fiducialFallbackChain`, `scanHorizontalRib`/`scanVerticalRib`): the two fixed candidates are tried first and unchanged (byte-identical output for the common all-four-ribs case), but once both fail, the code scans across whichever ribs actually have nonzero width — first a narrower "stay near your own corner" range so the three fiducials stay usefully spread out for orientation, then the full rib width, then (last resort) the same full-width scan again but ignoring the rib-text reservation entirely. "Minimum 3 fiducials" is a hard requirement — a panel is only useful for pick-and-place/AOI registration with all three present — while avoiding decorative rib text is only a preference, so a fiducial slightly under some text is the correct trade against having fewer than 3 fiducials at all. `isValidPosition` takes an `ignoreRibText` param for this; **it must be threaded through the final `addFiducial` re-validation too, not just the scan** — the scan can approve a spot with `ignoreRibText: true` and then `addFiducial(id, x, y)` silently re-validates with the default `false`, rejecting the very spot the scan just found. Caught by testing an extreme single-rib-only panel (only `sideRibBottom` nonzero) where this exact mismatch made the "ignore text" fallback a no-op.

**A second, independent bug surfaced during that testing**: the fiducial rib-text reservation (`topRibTextMinX/MaxX`, `bottomRibTextMinX/MaxX`) computed a mirrored `InfoText` entry's span as `[x, x+w]` — the same formula as a non-mirrored entry — when a mirrored entry actually renders growing *backward* from its anchor (`[x-w, x]`; `transformPoint` flips `nx` for `mirrored`). Every mirrored entry was reserving a second, phantom text-width of space on the wrong side of its anchor. Harmless-looking on a normal 110mm panel (the inflated zone still fit with room to spare), but on a 100mm panel with both side ribs removed it inflated the top-rib name text's reservation from its real ~48mm span out to ~96mm — consuming almost the entire rib and leaving zero valid positions anywhere, for ALL THREE fiducials at once. Fixed with a shared `infoTextSpanX(t)` helper (mirror-aware) used by both reservation blocks, replacing the ad-hoc `Math.min/max(t.x, t.x+w)` in each.

### Fiducials target the widest achievable spread, not a fixed floor

The fiducial-to-fiducial spacing check only ever enforced the bare physical minimum (`fiducialDiameter + clearanceOffset*2 + 2.0` — ~4mm at defaults): two fiducials 4mm apart don't overlap, but they're useless for an accurate pick-and-place/AOI affine fit, which wants three widely-spread points — real vision systems compute panel rotation/skew from the ANGLE between fiducials, so a wider baseline suppresses pixel-measurement noise amplifying into angle error. This wasn't hypothetical — the "minimum 3" scanning fallback above (which walks a rib in 2mm steps looking for the first valid spot) routinely produced exactly this: three fiducials clustered within a 25mm span on a crowded panel, two of them under 10mm apart.

First fixed with a tiered retry (`[20, 15, 10, physicalMinFidSpacingMm]`, widest-first, first success wins) — later **superseded** by a search for the actual widest spacing each specific panel can achieve, per explicit user request ("prefer the widest achievable spread given the panel size") rather than settling for a fixed floor. `isValidPosition`'s fiducial-distance check reads a shared `minFidSpacingMm` variable, and `attemptAllAtSpacing(spacing, allowIgnoreRibText)` places all three corners from scratch at a given threshold — restarting together, not "keep whichever corners already succeeded, retry only the failures," avoids an early corner greedily claiming a spot that leaves no room for a later one, when a different choice for the early corner would have. `widestSpacingSearch` tries a descending sequence of candidate spacings (`spacingSearchSteps = 48`, evenly dividing `[physicalMinFidSpacingMm, diagonalMm]`) and keeps the FIRST — i.e. widest — one that succeeds.

⚠ **This is a linear descent, deliberately NOT a binary search**, even though a binary search would need far fewer `attemptAllAtSpacing` calls. Binary search needs `attemptAllAtSpacing` to be monotonic in `spacing` — success at a wide spacing implying success at every narrower one — and that does NOT actually hold here. `fid_bl` is spacing-invariant (no other fiducial exists yet when it's placed), but `fid_br` and `fid_tr` each take the FIRST candidate that clears their deterministic scan order; as the spacing threshold changes, an EARLIER (closer) candidate can newly become valid and get chosen instead of the one used at a different threshold — which can shift `fid_br` into a position that leaves LESS room for `fid_tr` than a narrower spacing would have. A bisection implementation of this was tried and confirmed live to converge on a worse result than a directly-achievable wider spacing on a real test panel (the midpoints it happened to probe landed on a worse `fid_br` placement and falsely reported failure, permanently discarding the wider half of the search range it should have kept). The linear scan can't make that mistake: it tests real candidate spacings in descending order and keeps the first that works, so it can never do worse than any individual spacing it tests. The step count is a FRACTION of the range (not an absolute mm step), so resolution scales with panel size automatically while keeping the number of placement attempts — and thus runtime — bounded regardless of panel size (verified under ~15ms even on a 4×4 stress-test panel).

⚠ **The search runs in TWO PHASES** (`widestSpacingSearch(false)` then, only on failure, `widestSpacingSearch(true)`), not one search that happens to reach the `ignoreRibText` fallback tiers when convenient. A single search across the full chain (spacing and text-avoidance both relaxing together) pushes spacing as wide as the loosest rule allows — which routinely means landing on an `ignoreRibText` position purely to buy a few more mm of spread, even though a slightly tighter but otherwise completely clean spacing was available. Confirmed live: a 100mm-wide panel placed `fid_tr` directly under the customer/PCB name text, when backing off to a still-wide-enough spacing avoided it entirely. `ignoreRibText` exists ONLY to guarantee "minimum 3" as a last resort — it must never be spent on spacing that clean placement didn't need.

Also bumped `fidHalfSpan` (the fiducial's rib-text collision radius) by an explicit `marginBeyondClearanceMm = 1.5` beyond the bare mask-clearance geometry — real panels were landing text and pinning holes only ~1mm from a fiducial's edge, technically clear but too tight to trust against real fab registration tolerance.

### Rib-text reservation must be disjoint intervals, not one merged envelope

The fiducial rib-text reservation (`topRibIntervals`/`bottomRibIntervals` in `collidesWithRibText`) used to track each rib's reserved X-range as a single `{minX, maxX}` envelope — fine when a rib carries only one contiguous block of text, but the bottom rib routinely carries TWO, far apart: the real left-side overflow text (`generatePanelMetaText`'s tier 2) and the worst-case right-side per-layer-label reservation, with a large genuinely-empty gap between them on any panel wide enough. Merging both into one `[min, max]` span marks that entire empty middle as reserved too.

Confirmed on a real 176.5mm-wide 2×2 panel (top+bottom ribs only, no side ribs): the left overflow text sat at `[9.5, 47]` and the worst-case right zone at `[131, 175]`, merging into a single `[9.5, 175]` "reserved" span — i.e. the *entire* bottom rib. `fid_bl` and `fid_br` (whose whole purpose is to anchor the bottom-left and bottom-right corners) had nowhere left to go there at all, and both got pushed up to the top rib instead — landing all three fiducials clustered on one edge, exactly the clustering the tiered-spacing fix above was supposed to prevent. The scanning fallback and the spacing tiers were both working correctly; the input they were working from was wrong.

Fixed by tracking each rib's reservation as a **list of individual intervals** — one per real `infoText` entry (via `infoTextSpanX`) for the left side, plus the worst-case reservation as its own separate interval for the right side — and checking a candidate against each interval independently in `collidesWithRibText`, rather than folding them into one min/max pair. The real middle of the rib, where nothing is actually printed, is correctly seen as clear again. Top-rib text already only ever produces one contiguous block per line group in practice, but is tracked the same way for consistency and to not repeat this exact class of bug if a future change ever gives it disjoint content too.

### `collidesWithRibText` had no left/right-rib case at all, and its band checks weren't clearance-inflated

Three separate bugs found via a real customer panel plus a targeted randomized sweep (~400 configs across two seeds, varying PCB size, grid, rib widths, fiducial diameter/clearance, and font size), all in the same fiducial/rib-text collision machinery documented in the two sections above:

1. **No left-rib/right-rib case existed at all.** `collidesWithRibText` only ever checked the horizontal top-rib and bottom-rib text (X-intervals within a Y-band) — there was no equivalent check for the VERTICAL side-rib text `generatePanelMetaText`'s tier 3 places on the left/right ribs (rotation 90°, "PCB WxHmm"/"Panel WxHmm" etc., only rendered once both ribs are present and the top/bottom tiers ran out of room). A fiducial's side-rib fallback candidate — the one that centers it inside the left/right rib once the primary bottom/top-rib candidate is rejected — could land directly on this text with nothing to stop it. Fixed by adding `leftRibBandX`/`rightRibBandX` (an X-band, transposed from the horizontal case's Y-band) plus `leftRibIntervals`/`rightRibIntervals` built from `infoTextSpanY` (the Y-axis analogue of `infoTextSpanX`, derived from the same `transformPoint` rotation math — for a 90° entry the local reading axis maps onto world Y, so the same mirrored/non-mirrored growth-direction rule applies there instead).

2. **Band membership itself wasn't inflated by `fidHalfSpan`.** The existing X-interval (or new Y-interval) check was already inflated by the fiducial's own clearance radius, but the coarser "is this candidate even near this rib" band check (`y >= topRibBandY.min && y <= topRibBandY.max`, etc.) was a hard cutoff on the fiducial's CENTER point only. A fiducial's center can sit just outside a band while its physical clearance disc still reaches into it — confirmed live: `fid_tr` landed a few mm below `topRibBandY.min` (reading as "on the PCB grid, not the rib") while its clearance radius still overlapped the bottom-most of several stacked top-rib text lines. Fixed by inflating all four band checks by `fidHalfSpan` too, symmetric with how the interval checks already work.

3. **`worstCaseBottomRibLabelZone` ignored `generateLayerLabels`'s own hole-avoidance shift.** The reservation for where the eventual real per-layer labels will land was anchored at the fixed, unshifted `panelWidth - 17` / `panelWidth - 30` positions — but `generateLayerLabels` itself runs the real labels through `clearHolesAlongAxis` against `toolingHoles`, which can shift the anchor away from a nearby hole. A real label ending up shifted further than the (unshifted) reservation assumed let a fiducial land under it — consistently ~0.8mm inside the real label's edge across many random panel sizes (the shift itself doesn't scale with panel size, only with hole geometry near the corner). First fix: pass `toolingHoles` through and run the SAME `clearHolesAlongAxis` call with the worst-case width to get a shifted reservation — but this alone wasn't sufficient (see below).

   ⚠ **The shifted-anchor-alone reservation is still not a reliable superset.** `clearHolesAlongAxis`'s retreat-vs-advance choice depends on the SPAN WIDTH, and a real label is almost always narrower than the worst-case ("Bottom Copper") string — so a real label can collide with a hole the wider worst-case span doesn't (nothing to shift for), or the two can resolve the same collision with different shift amounts. Confirmed live: a real "Top Copper" label shifted away from a hole while the worst-case-width span at the same starting anchor found no collision there at all. Fixed by having `worstCaseBottomRibLabelZone` union FOUR candidate spans — the worst-case width at both the unshifted AND the shifted anchor, for both the top-group and bottom-group directions — rather than trusting either alone. This is a cheap, robust superset rather than an attempt to analytically predict which specific width triggers which shift.

### Fiducials now place BEFORE rib text, not after — text avoids the fiducial, not vice versa

⚠ **The three sections above describe a design this supersedes.** `topRibIntervals`/`bottomRibIntervals`'s `infoText` loop, `leftRibIntervals`/`rightRibIntervals`, and `infoTextSpanX`/`infoTextSpanY` are gone — `collidesWithRibText` now only checks the bottom rib's RIGHT-side worst-case per-layer-label reservation (`worstCaseBottomRibLabelZone`, still real and still needed — see below). The rest of that machinery existed to let a fiducial avoid ALREADY-PLACED real text; it's gone because fiducials no longer wait for that text to exist.

**What changed and why.** A real customer panel (no side ribs, 2×2 board, 176.5mm wide) showed a fiducial visually overlapping a hole and the revision/date text at the SAME bottom-left corner, and the equivalent overlap at bottom-right between a fiducial and the per-layer labels. The requirement, stated directly: each corner should read, moving inward from the panel edge, **reference hole → tooling hole → fiducial → text** (revision/date on the left, per-layer labels on the right) — matching the top-right corner's existing (already-correct) hole-then-fiducial order.

The first fix attempted was the smaller one: keep the existing text-before-fiducial order, but have TEXT pre-emptively reserve a zone at the fiducial's nominal candidate position (`sideRibLeft + 15` / `panelWidth - sideRibRight - 40`) before laying itself out, mirroring `worstCaseBottomRibLabelZone`'s own "reserve before the real element exists" precedent. This was **provably insufficient**: the fiducial's own widest-spacing search can and does move it well away from that nominal candidate, and a reservation based on the wrong estimate fails in BOTH directions — too narrow (text still overlapping the fiducial's real position) and, confirmed on the same real panel, too wide (text needlessly shoved rightward into a REAL hole's clearance zone to avoid a fiducial that never actually landed near there — trading one overlap for a different one, over-correcting because the guess and reality disagreed).

**The actual fix: reorder `computePanel` so fiducials are placed BEFORE `infoTexts` is populated**, then pass the real, final `fiducials` array into `generatePanelMetaText` (a new parameter) and into `generateLayerLabels` (also a new parameter, threaded through from `store.ts`'s call site via `result.fiducials`). Both functions fold fiducials into their existing `clearHolesAlongAxis` obstacle lists via a new `fiducialsAsHoles(fiducials, ribYMin, ribYMax)` helper — `fid.clearance` is already the mask keep-out ring's outer diameter (see `clearanceOffset`'s derivation), so no extra span math is needed; `clearHolesAlongAxis` adds its own buffer on top, same as for real holes. Filtered to the Y-band of the rib being laid out, since a fiducial that (via its own fallback chain) ended up on a DIFFERENT rib must not phantom-block text on this one. This has no guessing problem: it's the fiducial's REAL position, always.

**What fiducials still can't see** — the RIGHT-side per-layer-label worst-case reservation is unchanged and still necessary, because `generateLayerLabels` itself doesn't run until much later in `store.ts`, once the customer's actual Gerber layer list is known — well after this fiducial's position is already fixed and can't be revisited. Belt-and-suspenders: the fiducial still avoids the WORST-CASE guess at that future zone, and the real labels (once they exist) also avoid the real fiducial via `fiducialsAsHoles` — two independent, self-consistent checks rather than one trying to be exactly right.

⚠ **This is NOT byte-identical for panels with side ribs present**, unlike most fixes in this file. With `fid_bl` no longer needing to dodge real text that doesn't exist yet at placement time, its NOMINAL candidate succeeds more often — confirmed on `DEFAULT_PANEL_CONFIG` (5mm ribs all around, 2×3 grid): `fid_bl` moved from `(1.5, 2.5)` to `(20, 2.5)`, its clean nominal spot instead of a fallback crammed near the panel's corner margin. That shift cascades into `fid_br`'s own candidate/spacing search (the widest-spacing search is non-monotonic and cross-corner-dependent — see "Fiducials target the widest achievable spread" above), which is why `fid_br` also lands somewhere different (still hole-clear, still ≥3 fiducials, still well-spread — just not the same spot as before). Every other constraint (`isValidPosition`'s hole/grid/spacing checks) is untouched, so the new output is a different but equally valid solution, not a regression — verified directly against the real 176.5mm no-side-rib panel (all four corners now read hole → hole → fiducial → text) and against the default with-side-ribs config (3 fiducials, well-spread, zero hole/text overlaps).

### Layer-label-to-hole clearance was too tight in practice

`generateLayerLabels`'s and `generatePanelMetaText`'s hole-avoidance (`clearHolesAlongAxis`, see the two sections above) used a `holeClearanceMm` of 1.0 — enough to technically clear a pinning/tooling hole, but on a real exported panel this left only ~1.1–1.2mm between the label text and the hole edge, which read as "the label is placed near the hole" even though nothing actually overlapped. Widened to 2.5mm in both call sites (`generateLayerLabels` and `generatePanelMetaText` — kept identical, with a comment cross-referencing the other so they can't drift), which on the same test panel doubled the real gap to ~2.6–2.7mm. Purely a constant change; the clearing algorithm itself was already correct (see the sections above for that history).

### Panel Y origin — `sideRibBottom`, not `sideRibTop`

`computePanel` works in CAM350's first quadrant: **Y up, origin at the panel's
bottom-left**. The PCB grid therefore starts at `config.sideRibBottom`, and
`sideRibTop` is only ever reached via `panelHeight − sideRibTop`.

`pcbPositions.y` used to be computed from `sideRibTop`, which is invisible with
the default symmetric 5/5 ribs but offset the entire grid by
`(sideRibTop − sideRibBottom)` for any asymmetric panel. Because the
tooling-hole exclusion zone correctly derives from `sideRibBottom` (in two
places), it then no longer described where the PCBs actually were, and holes were
placed on top of boards: measured on a 2×2 panel with `T=20 B=5`, five
tooling/reference holes landed at Y=77 while the PCBs spanned Y=20..82. Fixed;
symmetric-rib output is byte-identical, so no existing panel changes.

If you touch grid placement, the invariant is that these must all agree:
`pcbPositions.y`, both `gridBottom`/`gridTop` computations, the rib-text
generators (`ribHeight = sideRibBottom` for the bottom rib, `sideRibTop` for the
top), and the hole placement (`sideRibBottom/2` low, `panelHeight − sideRibTop/2`
high).

### Routing (depaneling) — conventions that must not drift

`src/lib/routing/` turns a computed panel into router tool paths, emitted as
Gerber, Excellon `.rou`, **and** LinuxCNC G-code. Full rationale + the Phase A/B
history: `ROUTING_ROADMAP.md`.

- **Cutter compensation is applied exactly once**, in `geometry.ts`'s `offsetRectOutward`. Every `RoutePath.points` is already TOOL-CENTER, offset outward from the finished board edge by the bit radius — emitters must never offset again, and the export README states the convention explicitly because a fab reading a route layer cannot otherwise tell centerline from board edge.
- ⚠ **`pathGap = tabWidth + bitDiameter`**, not `tabWidth`. The cut is the path swept by a disc of radius `r`, so a path gap of `g` leaves `g − 2r` of material. Using `tabWidth` as the gap directly makes every breakaway tab one bit-diameter too narrow — a silent scrap bug.
- ⚠ **Mouse-bite holes are pulled OUTWARD from the board's own edge line** by `mouseBiteHoleDiameterMm/2 + mouseBiteEdgeClearanceMm` (default clearance 0.2mm) — never straddling the cut line (half the drilled hole inside the finished board, half outside), which is the traditional convention but leaves a semicircular nub of drilled hole on the finished edge after snapping. `RouteTab.center` itself stays on the true edge (it's what the solid-tab bridge visualization is measured from); only the HOLES get the outward pull, computed via `pullOutward()` in `plan-routing.ts` and shared by both the bbox loop and `planContourPcb`. Two PCBs facing across a shared gap get *two* hole rows, each pulled toward its own board's scrap side; that is correct, since each board needs its own perforation to snap flush.
- ⚠ **Tab positions are always measured in one PANEL-GLOBAL direction** — left-to-right for horizontal edges (bottom AND top), bottom-to-top for vertical edges (left AND right) — never in `rectEdges`' own a→b perimeter-walk direction, which reverses for 'top' and 'left' (needed so the wrap-around stitching logic sees a continuous CCW walk). A symmetric auto-spaced tab set (`evenTabCenters`) survives that reversal by luck — an evenly-spaced-with-equal-margins set is symmetric under reflection — but a real customer file using a custom `tabPositionsMm` override hit exactly this: two facing PCBs across a panel gap measured "distance from edge start" from OPPOSITE ends, landing tabs at different absolute X (or Y) positions. With `mergeCoincidentPasses` sharing one pass down the gap centreline, each board's own pass then cut straight through its NEIGHBOUR's now-misaligned tab, silently destroying tabs on both sides with no error or warning. Fixed by mirroring the desired position (`edgeLen - d`) before it's used for the interrupt span or `boardEdgePoint`, for 'top' and 'left' specifically — the tab's displayed ID still uses the un-mirrored value, so labels are unaffected and the fix is byte-identical for the (overwhelmingly common) symmetric auto-spaced case.
- **Routing needs `gap ≥ bitDiameter`.** `DEFAULT_PANEL_CONFIG.gapX/gapY` is 0.5mm, so every new panel starts in conflict for all three bit presets — the tab surfaces this as an `error` with a one-click fix that patches the gaps *and* rebuilds the panel (a patch that changes panel geometry invalidates `panelResult`).
- **Rib margins are measured from `pcbPositions` + `panelWidth/Height`, never from `config.sideRib*`** — deriving them from the real layout keeps the routing engine correct regardless of how the grid origin is computed. (`computePanel` used to place PCBs from `sideRibTop` while the tooling-hole exclusion zone derived from `sideRibBottom`; that is now fixed — see "Panel Y origin" below — but measuring the layout is still the right habit.)
- **`RoutingConfig` is a separate, deliberately FLAT store slice**, not new `PanelConfig` fields. `updateRoutingConfig` is a shallow merge; a nested object would need a manual re-spread in both it and `resetRoutingConfig`, which is exactly the `PanelConfig.drillFormat` trap. Keeping it out of `PanelConfig` also gives the existing panel export zero regression surface.
- ⚠ **A stale routing plan is cleared, never kept.** Tool paths are panel-absolute, so a `.rou` carrying a *previous* panel's coordinates is a real fabrication-scrap risk. `computePanelResult`, `resetPanelConfig`, `clearLayers`, `setTargetUnit`, `rotateAllLayers` and `alignDrillLayersToBoard` all null out `routingResult`; changing routing config only marks `routingStale` (the panel then prompts to regenerate — it never auto-recomputes).
- **Route files own their own aperture namespace** because each is written as its own file, so the `findMaxDCode` collision dance that overlay features inside customer layers require does not apply here. Unlike `generatePanelOutlineGerber` (which hardcodes 3.4mm to byte-match a CAM350 sample) the route Gerber respects `OutputFormat`.
- **Mouse-bite holes default to their own `_MouseBites.drl`**, which keeps the CAM350-verified `_Drill.drl`/`_PINN.drl` output byte-identical; folding them into the main drill is an opt-in checkbox.
- Non-rectangular outlines route the **real traced board profile** by default (`pcbOutlineMode: 'auto'`) — see "Contour routing" below. Bounding-box routing is still available (explicit `'bbox'` mode) for the cases contour tracing can't handle, and still raises the `outline-not-rectangular` warning when it's what's actually going to run.
- ⚠ **The `.rou` dialect is provisional** — there is no CAM350 rout export in the repo to diff against (only `Panel_border.gbr` and `pinn.drl`). It emits the standard Excellon-2 rout form and is labelled provisional in the README and UI.
- The viewer's route swath deliberately **omits `vectorEffect="non-scaling-stroke"`** (unlike nearly everything else in `panelOverlayContent`) because its width *is* the physical material the cutter removes — a non-scaling stroke would make the preview lie about the cut.
- ⚠ **Tooling/reference holes must clear the routed path, not just the PCB grid.** `computePanel`'s `addHole` only ever rejected a hole for landing *inside* the grid rectangle — it had no notion that a router bit cuts a path OFFSET OUTWARD from that same grid edge by the bit radius, so a hole sitting just outside the grid (correctly, in the rib) could still fall inside the swept cut. The Y-position of every corner tooling/reference hole used to be dead-center of the rib (`sideRibTop/2` etc.) — confirmed live (both via a standalone routing-planner reproduction and on a real panel with no side ribs, where this same rib-half-width formula still governs whichever ribs DO remain): with the default 5mm rib, 2mm bit, and 2mm tooling hole, that left only 1.5mm of actual gap against a cut that needed 2mm — a router path running straight through a pinning hole, on every corner, panel-outline or per-PCB, bbox or contour, ribbed or not. Fixed by wiring up `toolingHoleInset` (a "Pinning Inset" field that already existed in the UI but was pure dead code — assigned, never read) as the hole row's distance from the PCB **grid edge**, replacing `sideRib*/2`, at a new 3mm default (previously 5mm, but unused so the old value was never actually load-bearing). Reference holes share the exact same Y for the same reason fiducial-rib-text sharing does — they sit in the same rib "row" by corner-alignment design, so giving them a different formula would just reintroduce the collision for them specifically.
- ⚠ **The panel-compute-time hole inset is a good default, not a proof.** It's sized for a representative bit (the largest standard preset, 2mm) and the default hole diameter, but panel geometry is computed before the user has necessarily picked a bit, and can't see a custom bit or custom hole diameter either — nor the slightly different corner geometry a contour-mode round join produces versus a bbox miter (confirmed live: even after the inset fix, one contour-routed corner on a notched/chamfered board still landed ~1mm inside a hole a plain rectangle wouldn't have touched at that same corner). The authoritative check is `planRouting`'s own `hole-routing-collision` issue (`plan-routing.ts`), which runs against the REAL computed `RoutePath` geometry — panel-outline, bbox, and contour paths alike, generically, no per-mode branching — rather than trying to predict it. Advisory only, matching `rib-too-narrow`'s existing precedent: it names the offending hole and the exact shortfall, but doesn't block generation.
- **Protective tabs actually eliminate the hole/path collision, rather than just tightening the margin.** Following a real-panel report that a pinning hole still read as uncomfortably close to the routed edge even after the inset fix above, `planRouting`'s per-PCB loop now forces a tab wherever a tooling/reference hole sits within `bitRadius + holeRadius + 0.5mm` of that edge — a tab means the cutter genuinely never removes material across that span, which protects the hole regardless of how little room a narrow rib actually has (a fixed clearance margin can't always be afforded; skipping the cut there always can). This is a *response* to the `hole-routing-collision` check, not a replacement for it — that check still runs against the final paths and will still fire if a tab genuinely can't be placed (e.g. `tabStyle: 'none'`, or a contour tab landing across too much curvature and getting skipped — see `contour-tabs-skipped` below).
  - **bbox mode**: `centersAlong` (the per-edge tab-center list, previously either the user's `tabPositionsMm` override or `evenTabCenters`) gets each qualifying hole's edge-projection appended, in the same "dGlobal" convention (post `isReversedEdge` correction) the rest of the loop already uses — the existing interrupt-span / tab-emission code handles the merged list with no other change.
  - **contour mode**: computed per PCB *instance*, not once in file space — mirrors the existing `extraSilentDs` mechanism (cross-PCB tab-destruction protection) via `nearestArcLengthOnRing`, but unlike `extraSilentDs` (a silent gap only, because some OTHER instance already owns that tab) a hole-protective `d` gets a REAL `RouteTab` emitted — no other instance owns it. Routed through `findSafeTabCenter` (same curvature guard the ring's own tabs use), so a hole sitting right at a sharp corner nudges to a safe nearby spot instead of being silently dropped; a hole whose only safe position is skipped is now covered by `contour-tabs-skipped` too, with detail text naming the hole cause specifically (not just tab-count-vs-perimeter).
  - Verified with a randomized-config script (bbox and contour, ribbed and rib-less, default and deliberately-tightened 4mm ribs at the largest 2mm bit preset): zero hole/path collisions and zero `hole-routing-collision` issues across every scenario, including the contour round-join corner case above that survived the inset fix alone. Sub-10ms even on a stress-test 4×4 panel.
- ⚠ **The panel-outline pass can physically coincide with a per-PCB tab, and used to cut straight through it.** "The panel is cut from a larger sheet, so it gets no tabs: one closed loop" is correct ONLY when the panel-outline cut is physically distinct from any per-PCB edge — true whenever a rib separates them. But with a side rib REMOVED (`sideRib* === 0`), the outermost PCBs' edge on that side and the panel's own outer edge are offset outward from the exact same physical boundary by the exact same bit radius — the SAME line. A panel-outline loop generated independently, with no awareness of what per-PCB tabs already exist there, cuts straight through them. Confirmed live: a no-side-rib panel's left-edge break tab sat directly under a fully continuous panel-outline pass — same failure mode as the already-documented "coincident pass destroys tab" class of bug above (tab misalignment / mouse-bite-destruction), just a different pair of paths coinciding.
  - Fixed by moving panel-outline generation to AFTER per-PCB paths/tabs are fully built (it used to run first), then reusing those ALREADY-COMPUTED tab positions as silent interrupts on whichever of the panel-outline's four edges has `sideRib* === 0` — exactly the `extraSilentDs` pattern contour mode's cross-PCB tab protection already established (a gap with no NEW `RouteTab`, since the owning PCB's tab already represents this physical location), generalized to a different kind of "another path already has a tab here."
  - Implemented via `nearestArcLengthOnRing` + `buildArcLength`/`splitClosedByTabs`/`extractArcSpan` (the SAME closed-ring arc-length utilities contour mode's own outer-boundary splitting already uses) rather than hand-rolling rectangle-specific edge-splitting math — the panel-outline rectangle is just a 4-corner closed ring to these functions, no different from a contour's offset ring. This sidesteps having to independently re-derive which direction each of the four rectangle edges measures distance-along in (`rectEdges`' own CCW walk reverses for 'top' and 'left', the exact class of bug the tab-alignment section above documents) — `nearestArcLengthOnRing` projects an absolute point onto the ring directly, no edge-direction bookkeeping needed.
  - Membership test: a tab counts as "on the panel's outer boundary" only when its `edge` matches AND its owning PCB is in the outermost row/column for that side (`col === 0` for left, `col === maxCol` for right, etc.) — an interior PCB's tab (facing a neighbour across a gap) must never be treated as panel-boundary-adjacent even if, coincidentally, `sideRibLeft === 0` for that panel.
  - When no side rib is zero (the common case), zero tabs ever qualify and the code takes the original single-closed-loop path unchanged — verified byte-identical to the pre-fix output for every ribbed control case tested.

### Contour routing (non-rectangular boards) — conventions that must not drift

Shaped boards (rounded corners, chamfers, curved edges, interior cutouts) are
routed as their **real traced profile**, not a bounding box. Full design
rationale and staging history: the "Contour routing for non-rectangular PCBs"
plan referenced from `ROUTING_ROADMAP.md`.

- **Three new files, one job each.** `src/lib/board-contour.ts` is the ONLY
  code that ever reads a tracespace `BoardShape` — `boardShapeToContour`
  (pure adapter) and `traceBoardContour` (async: parse + plot + adapt one
  outline layer). `src/lib/routing/offset.ts` is the pure offset/tab engine
  (`offsetClosedRing`, arc-length/tab placement) — zero tracespace or store
  imports. `src/lib/routing/plan-routing.ts`'s contour branch
  (`computeContourGeometry`/`planContourPcb`) is the orchestration layer that
  turns the two into `RoutePath`/`RouteTab` objects, mirroring how the
  pre-existing bbox loop sits on top of `geometry.ts`'s primitives.
- **Orientation convention: outer ring CCW, hole rings CW, offset always to
  the RIGHT of travel.** This is uniformly outward for the board's outer
  boundary and inward for interior cutouts with no sign flag threaded through
  the code — verified against a CW unit square before relying on it (see
  `offset.ts`'s own header). The join-type rule (round join vs. analytic
  miter) falls out of the SAME turn-sign test regardless of which ring type
  it's applied to; it's a local fact about the vertex relative to the offset
  direction, not "convex on a CCW ring" — that phrasing in earlier notes was
  calibrated for the outer-boundary case only.
- ⚠ **`pcbOutlineMode` is `'auto'` by default** (contour, EXCEPT when the
  outline is already a plain rectangle, where bbox produces identical output
  for less work — `resolveOutlineMode` in `plan-routing.ts`). This was
  deliberately flipped from `'bbox'` only after the whole pipeline was built
  and verified end to end; a shaped board routed under the old default would
  have been silently over-cut.
- ⚠ **A contour trace failure is a blocking error, never a silent fallback to
  bbox.** The bbox is *known-wrong* for a shaped board — offering it under an
  error banner would invite downloading scrap toolpaths anyway. Same for an
  offset that collapses, an ambiguous nesting classification, or a panel with
  more than one depth-0 outer boundary (the file describes several boards,
  not one PCB) — every one of these emits ZERO per-PCB paths plus an `error`
  issue rather than a plausible-but-wrong path.
- **Cutouts are emitted before the outer profile**, per PCB — interior
  features must be milled while the board is still fully supported by the
  panel. Just array order (`planContourPcb`), but it directly determines
  `.rou`/G-code sequence.
- **Trace once, offset once, tab once — in the outline file's own space.**
  `planRouting`'s contour branch computes `ContourGeometry` a single time,
  then only TRANSLATES it per panel position (`dx = pos.x -
  outlineBoundsMm.minX`, ditto Y). ⚠ That datum is `RoutingPlanContext.outlineBoundsMm`
  — the outline layer's own (arc-blind) `GerberLayer.bounds`, the SAME
  convention `gerber-exporter.ts`'s `globalBaseOffset` uses — NOT
  `BoardContour.boundsMm` (arc-accurate). The two differ by the arc bulge;
  using the wrong one puts the route out of register with the copper/mask
  artwork by that amount.
- **`generateRouting` is async and traces its own contour** (`store.ts`) —
  never reads `BoardView.boardContour` (fire-and-forget, can resolve out of
  order, skipped by `computePanelResult`). It aborts with NO state change if
  `layers`/`panelResult` moved on during the trace (reference-identity
  staleness guard — every mutating store action replaces those refs
  wholesale, so this check is exact, not heuristic).
- **`findOutlineBoundsLayer` (`store.ts`) is the one place "the outline
  layer" is found**, used by `computePanelResult`, `generateRouting`, and
  `generateGcodeFilesAction` — before this was extracted, `computePanelResult`
  required `.visible` and `generateRouting` didn't, so a hidden outline layer
  could silently drive routing math while being excluded from panel sizing.
- **Tabs spread evenly by arc length around the whole closed contour** — the
  bbox path's `tabTop/Bottom/Left/Right` edge toggles don't apply and are
  hidden in contour mode; `tabsPerContour` replaces `tabsPerEdge`. A
  **curvature guard** (`findSafeTabCenter` in `offset.ts`) rejects placing a
  tab across more than ~20° of accumulated turning (a corner or a tight arc),
  nudging up to one `pathGap` before giving up and skipping that tab —
  `contour-tabs-skipped` reports how many.
- `dedupeCoincidentSegments` (`geometry.ts`) is a **spatial hash**, not the
  original O(n²) scan — contour mode's segment counts (tens of thousands on a
  large panel) made the naive version impractical. Verified
  element-for-element identical output via a randomized harness before
  replacing it; see the function's own header for the 3×3-neighbourhood
  provable-superset argument.
- ⚠ **Contour mode still doesn't merge coincident PASSES between adjacent
  PCBs** (each board's outline is routed fully independently — redundant
  double-cutting on a shared line, not unsafe by itself), **but it DOES
  guard against coincident-pass TAB destruction**, which is a real
  fabrication defect, not just inefficiency. At `gap == bit`, two facing
  PCBs' offset boundaries land on the exact same physical line — and unlike
  bbox mode's rectangle tabs (aligned across facing edges by the
  edge-direction-canonicalisation fix below), contour tabs are placed by
  whole-perimeter arc length with no per-edge concept to keep them aligned
  between two DIFFERENT PCB instances. Without a check, a neighbour's own
  uninterrupted pass — having no reason to know about a tab it doesn't own —
  would cut straight through it. The per-PCB loop in `planRouting`'s contour
  branch pre-computes every instance's tab centres, then for each PCB checks
  every OTHER instance's tabs against its OWN boundary via
  `nearestArcLengthOnRing`; a match within a bit-radius contributes an
  `extraSilentDs` interrupt — same silencing as an owned tab, but with no
  `RouteTab` emitted (the owning PCB already has that one). Confirmed by a
  differential test: disabling this check on the real WIFI V6 fixture across
  a dozen grid/tab-count combinations produced 111 real cross-PCB
  tab-destruction cases; with it enabled, zero. `ContourGeometry.cutSpans`
  had to move out of the once-computed shared geometry into `planContourPcb`
  itself (it now depends on a PER-INSTANCE thing — its neighbours) — the
  file-space `outerPts`/`outerTable`/`tabPositions`/`cutouts` stay
  computed once, only the final cut spans are per instance.

### G-code (LinuxCNC) — conventions that must not drift

`src/lib/routing/gcode.ts` turns a `RoutingResult` plus the panel's own imported
drill holes into G-code, confirmed against 7 real production files from the
user's actual LinuxCNC machine (one cutting/routing program, six drilling
programs at different tool diameters). Unlike the Gerber/Excellon emitters,
there's exactly **one** real dialect in evidence, so this file is deliberately
concrete rather than a pluggable multi-dialect abstraction — extract a
`GcodeDialect` seam only once a second real machine shows up to generalize
from. Full rationale: `ROUTING_ROADMAP.md` §3.

- **One cutting program per router-bit diameter, one drilling program per distinct hole diameter** — mouse-bite holes and the panel's own imported drill hits that share a diameter are combined into the same file. This matches the shop's own workflow: LinuxCNC's manual tool change means separate programs per bit, not mid-file `T`-code changes.
- ⚠ **`generateRouteGcode` and `generateDrillGcode` use two deliberately DIFFERENT templates** — the real sample files' own two post-processor paths disagree on where `G21` sits, whether the dwell is repeated, and even trailing whitespace. Don't unify them into one shared template; that would mean guessing which convention is "correct" when the shop's own tooling doesn't agree with itself.
- **Sequencing needs no tab-specific logic** — a `RoutePath` boundary already IS a retract (the routing planner only splits a path at a tab or a dedup boundary), and a point-to-point move *within* a path is already a continuous cut. This was confirmed by diffing the real cutting file's retract count against its own corner-vs-tab layout.
- **`DRILL_FEED_TABLE_MM_PER_MIN` (`gcode.ts`) is looked up per tool diameter by default** (`GcodeContext.autoFeedByDiameter`, default true) — `resolveDrillFeedMmPerMin` piecewise-LINEARLY interpolates between seven REAL (diameter, feed) pairs read directly from the shop's own drilling files, clamping to the nearest endpoint outside that range rather than extrapolating. This reverses an earlier, more conservative decision to use one uniform `drillFeedMmPerMin` for every diameter — that was the right call with only six data points and no visible shape to them; a seventh real point (2.15mm) later made the step-down shape (2000 down to 500 mm/min, smaller bits faster) clear enough to encode directly. Still not a fitted formula — piecewise-linear interpolation between real measurements is an honest encoding of the vendor's own data, not invented "smart" science, and `drillFeedMmPerMin` remains available as the flat rate when `autoFeedByDiameter` is turned off.
- **Drill/slot order defaults to greedy nearest-neighbor travel optimization** (`GcodeContext.optimizeDrillOrder`, default true) — before this, `generateDrillGcode` just walked `holes` in whatever order it was handed: raw Gerber/Excellon flash order within one board, then PCB-by-PCB across a panel (`pcbPositions` grid order), with zero regard for travel distance between consecutive holes. `nearestNeighborOrder` (`gcode.ts`) repeatedly picks whichever remaining hole/slot is closest to the machine's current position, starting from `(0,0)` (the same home-position convention `generateRouteGcode`'s explicit `G00 X0Y0` uses) — a plain greedy nearest-neighbor pass, not a full TSP solve, which is NP-hard and unnecessary overkill for this. Slots chain onto wherever the last hole left the tool (or `(0,0)` if there were none), using the slot's `start` as the point being sought and its `end` as the new current position, since that's genuinely where the tool is after cutting it. O(n²) — deliberately not the spatial-hash approach `dedupeCoincidentSegments` needed, since drilling programs run to at most a few thousand holes per diameter (verified: 4000 random holes sorts in ~40ms), nowhere near the tens-of-thousands-of-primitives regime that forced that optimization. Turning it off preserves the exact raw pass-through order — useful for diffing against a real sample file byte-for-byte (as several of this file's other drilling-file comparisons do), or if a shop's own post-processor already reorders travel itself.
- Coordinates are always **explicit-decimal** (no zero suppression at all) — this dialect has none of the LZ/TZ inversion bug class Excellon output has to guard against.
- `generateGcodeFilesAction` (store.ts) collects the panel's own drill holes via `collectAllDesignsDrillHoles`/`collectAllDesignsDrillSlots` (multi-design-aware wrappers around the per-design `collectPanelizedDrillHoles`/`collectPanelizedDrillSlots` from `gerber-exporter.ts`) and folds them together with `collectMouseBiteHoles(routingResult)` before diameter-grouping — G-code drills mouse bites, the customer's real holes, AND, as of the fix below, tooling/reference holes.
  - ⚠ **Tooling/reference (PINN) holes were missing from the plain G-Code tab's drilling output** — `generateGcodeFilesAction` built its drill groups purely from component + mouse-bite holes, with no awareness of `panelResult.toolingHoles` at all, while the separate Meta-Panelization export (`generatePanelArrayFilesAction`) and the Excellon export (`generatePINNDrill`/`generatePanelizedDrill`) both already included them under the same `panelConfig.enableToolingHoles` gate. Reported live: a real board's "Regenerate G-Code" produced 8 drilling files vs. the Meta-Panel export's 10 for the same board, missing the tooling-hole diameter's second file and the reference-hole diameter entirely. Fixed by merging a `panelResult.toolingHoles`-derived `{diameterMm, holes}[]` group into the same list before diameter-grouping, mirroring `generatePanelArrayFilesAction`'s own merge exactly.
- ⚠ **Stale G-code is cleared, never kept**, same discipline as `routingResult`: `gcodeFiles` is nulled out everywhere `routingResult` is (every panel/layer-mutating store action, plus regenerating routing itself) — a `.NC` program carrying a previous plan's coordinates is a fabrication-scrap risk exactly like a stale `.rou`.
- G-code needs no viewer overlay of its own — it's a text serialization of the same `routingResult.paths` geometry the Routing tab's `route-overlay` group already renders.

### Meta-panelization (multi-panel-array CNC batch drilling)

A real shop workflow, distinct from ordinary panelization: the customer's CNC bed/raw-material sheet is bigger than one computed `Panel`, so multiple copies of that already-computed panel get tiled and drilled together in one run. `src/lib/panel-array.ts` holds the whole thing — pure functions, no store/React, same discipline as `routing/geometry.ts`.

1. **Rout `Border_Marks.gbr`'s L-shape corner marks into a blank sacrificial spoiler board.** These use the exact same per-corner arm geometry as `generatePanelBorderLShapeGerberCommands` (bottom-left: `(arm,0)->(0,0)->(0,arm)`, etc.), just applied once per array cell instead of once per panel — `generateBorderMarkPaths` returns one connected 3-point polyline per corner, sheet-absolute mm.
2. **Place each already-fabricated panel copy on the bed**, registering its corners against the scored marks, and tape it down.
3. **Run one batch drilling program** that drills every copy's component holes (+ tooling/reference holes) in a single pass — the entire point of tiling multiple panels is that drilling only needs the panel physically present, not yet routed/depanelled.

⚠ **Deliberately independent of `RoutingResult`** — mark-routing and batch drilling only need a computed `PanelResult` (for the cell size) plus the customer's own drill layers; depaneling each panel copy into individual PCBs is a separate, later, per-panel step through the existing Routing tab. `generatePanelArrayFilesAction` (store.ts) therefore only guards on `panelResult`, never on `routingResult`.

**`computePanelArray(panelWidthMm, panelHeightMm, config)`** fits as many copies as possible in a grid bounded by BOTH the CNC's travel limit and the material sheet on hand (whichever is smaller per axis), with a configurable inter-cell gap and outer margin — the standard "n items + (n-1) gaps fit in the available span" formula, solved per axis independently. Returns `null` (never a plausible-but-wrong layout) when nothing fits, even a single copy — same fabrication-honesty rule the routing engine's contour trace failure follows.

⚠ **"Shared marks at grid intersections" is achieved by capping the arm length, not by inventing T/+ mark shapes.** Each array cell gets its own complete, independent 4-corner mark set (this is the ONLY design that keeps every mark flush with its own panel's real corner, which is the whole point of a registration mark — a mark offset into the gap wouldn't line up with the panel edge the operator is actually registering against). To avoid near-duplicate marks cluttering a narrow gap between two cells, `PanelArrayResult.effectiveMarkArmLengthMm` clamps `config.markArmLengthMm` to at most half of `arrayGapXmm`/`arrayGapYmm` (and half of the cell's own dimensions, for a degenerately small cell) — so one panel's marks can never physically reach far enough to overlap a neighbour's. This was a deliberate simplification over classifying each grid intersection into L/T/+ shapes based on how many neighbouring cells touch it: that approach was explored and rejected as unnecessary complexity once it became clear the flush-corner requirement rules out any actual point-sharing between cells anyway (adjacent cells' corners are always `arrayGapXmm`/`arrayGapYmm` apart, never the same coordinate, for any nonzero gap).

**Gerber vs. G-code vs. Excellon** — `generateBorderMarksGerber` (panel-array.ts) is a standalone RS-274X file (own `%FS`/`%MO` header) purely for CAM visualization/reference; the PHYSICAL marks come from `generateMarkRoutingGcode` (routing/gcode.ts) milling the same paths directly at their drawn centerline — no cutter-compensation offset, since these aren't board edges to cut around, just scoring. `markCutDepthMm` is a separate config field from `GcodeContext.cutDepthMm` — the marks cut into a blank spoiler board, not the customer's own board + backer, and may legitimately need a different depth. `generateMetaPanelDrill` (gerber-exporter.ts) emits the tiled batch drill Excellon file by reusing the exact same low-level helpers (`generateDrillFormatHeader`/`emitExcellonToolBlock`/`formatDrillCoordinate`) as the ordinary per-panel `generatePanelizedDrill`, just fed pre-tiled `{diameterMm, holes}[]`/`{diameterMm, slots}[]` groups instead of walking `LayerFile[]` apertures itself — `tileHolesAcrossArray`/`tileSlotsAcrossArray` (panel-array.ts) do the tiling generically, translating every hole/slot by each array cell's own offset. The store action merges the customer's own component holes with the panel's tooling/reference holes (by diameter) BEFORE tiling, so every array copy still gets its own pinning holes for its later, separate per-panel routing step.

⚠ **`resolveExportDrillFormat`'s `panel` parameter is typed `Pick<PanelResult, 'panelWidth' | 'panelHeight'>`, not the full `PanelResult`** — it only ever reads those two fields (for auto-widening integer digits to fit the largest coordinate), and the meta-panel array needs to size the drill format against the ARRAY's much larger sheet dimensions, not the single panel's. Widening the parameter type to a `Pick` let the array code pass a plain `{ panelWidth: sheetWidthMm, panelHeight: sheetHeightMm }` literal instead of fabricating a fake `PanelResult`, with zero behavior change for every existing caller (a full `PanelResult` still structurally satisfies a `Pick` of it).

**Exports**: the Border_Marks Gerber + tiled Excellon drill ride along inside the main panel export ZIP's `Meta-Panelization/` subfolder (`exportPanelizedGerbers`'s new `metaPanel` param, gerber-exporter.ts) whenever generated — same pattern as how routing files already ride along via `writeRouteFiles`. The G-code (mark-routing + batch-drilling `.NC` files) has its own standalone `exportMetaPanelFiles` ZIP (mirroring the existing `exportRoutingFiles`/`exportGcodeFiles` precedent of multiple export granularities) and ALSO optionally rides along in the normal G-Code tab's `exportGcodeFiles` ZIP under its own `Meta-Panelization/` subfolder, so a session that generated both a normal single-panel job and a batch array gets everything in one download.

⚠ **Invalidation follows the panel/layers, not routing.** `panelArrayResult`/`panelArrayFiles` are nulled everywhere `panelResult` itself is (layer import/clear/rotate, `computePanelResult`'s early-returns and success path, `setTargetUnit`) — since the array layout is computed from `panelResult.panelWidth/panelHeight`. `alignDrillLayersToBoard` and `resetPanelConfig` only clear `panelArrayFiles` (not `panelArrayResult`) — drill geometry or tooling-hole/drill-format settings changing invalidates the generated file CONTENT, but not the array LAYOUT (cols/rows), which doesn't depend on either. Note `updatePanelConfig` (the general per-keystroke config editor, as opposed to a full reset) does NOT retroactively invalidate an already-generated `panelArrayFiles` bundle — unlike `routingStale`, there is no `panelArrayStale` flag/banner; regenerating is one click and cheap, and this was a deliberate scope cut given the feature's lower fabrication-safety stakes (a batch-drilling convenience layer, not the board's own tool paths).

The G-Code tab's UI (`gcode-panel.tsx`) distinguishes "never generated yet" from "generated and nothing fit" via a local `arrayAttempted` component-state flag — `panelArrayResult` is `null` in both cases, so gating the "nothing fits" warning banner on `!panelArrayResult` alone showed it immediately on page load, before the user had ever clicked Generate. Reset on `panelResult` changing, so a stale failure from a previous panel doesn't reappear for a brand new one.

### Panelization templates

Reusable "shop policy and machine facts" bundles across five config slices — `panelConfig`, `outputFormat`, `routingConfig`, `gcodeContext`, `panelArrayConfig` — so a customer doesn't re-enter the same rib widths, drill format, bit diameter, and spindle RPM on every job. Mirrors the `DfmTemplate` system (PRIVATE per user / SHARED published by staff, publicly readable so the CAM tool works logged-out, `PanelTemplate` model + `/api/panel-templates` + `/api/admin/panel-templates`, `src/lib/panel-template/templates.ts` mirroring `dfm/templates.ts` field-for-field) — but diverges from it in four deliberate ways, because copying that pattern verbatim would have been wrong for this feature specifically:

1. **Grid layout is never templated.** `PanelSectionSettings` (`src/lib/panel-template/types.ts`) is `Omit<PanelConfig, 'rows' | 'cols' | 'gapX' | 'gapY' | 'xyOverrides'>` — rows/cols/gaps are the genuine per-job input (the user's own framing: "generally a user will choose same settings often, except panel row, column and spacing options"), and `xyOverrides` is keyed by hole/fiducial ids generated for one specific panel's own geometry, meaningless applied to a different board. `extractPanelTemplateSettings`/`applyPanelTemplate` (store.ts) are the only two places that cross this boundary, and both respect it: extraction strips the five fields, application spreads the resolved `panel` section over the CURRENT `panelConfig` (not a fresh default) so grid fields survive untouched.
2. **Selection ≠ application.** Unlike `dfm-panel.tsx`, where picking a template immediately becomes `activeRules`, `panel-template-picker.tsx` only auto-*selects* a template for display on mount/dropdown-change — nothing is ever written to `panelConfig`/`outputFormat`/`routingConfig`/`gcodeContext`/`panelArrayConfig` except through the explicit **"Apply to Settings"** button, with **per-section checkboxes** (`PanelTemplateSection` = `'panel' | 'output' | 'routing' | 'gcode' | 'array'`) so applying a panel template can't silently overwrite a spindle RPM you already dialed in. This keeps the existing "nothing auto-computes" convention intact (panel/DFM/routing/G-code generation all require an explicit click) and avoids the alternative failure mode a DFM-style auto-apply would have here: template selection overwriting live config the user just typed.
3. **All-optional schema + generic deep merge, not per-field `.optional()` + hand-written defaults.** `dfm/types.ts` carries a standing warning that a field made required *after* templates exist retroactively fails validation for every saved row, with the non-throwing read path then silently substituting the baseline — a trap that's avoided today only by a human remembering the pattern for every new field. At ~60 fields across five types that discipline doesn't scale, so `panelTemplateSettingsSchema` makes every section `.optional()` AND every field within each section's schema `.partial()`, and `withTemplateDefaults` is a **generic recursive deep merge** (`deepMergeDefined`) over the five `DEFAULT_*` constants rather than a per-field `??` list. Adding a field to `PanelConfig`/`RoutingConfig`/`GcodeContext`/`PanelArrayConfig`/`OutputFormat` — or a whole new section — later needs zero changes here; old rows simply lack the key and inherit the current default. Verified with a dedicated backward/forward-compat harness (hand-written partial blobs, unknown-key blobs, garbage blobs through both the throwing and safe parsers) before any UI was wired up.
4. **The nested `drillFormat` field needs the recursive merge, not a shallow one.** `PanelConfig.drillFormat: DrillFormatConfig` is the one nested object among the five templated types, and it's the same shallow-merge trap `store.ts`'s `updatePanelConfig` documents — `deepMergeDefined` recurses into plain objects specifically so a template's `{ panel: { drillFormat: { unit: 'mm' } } }` merges field-by-field instead of replacing the whole sub-object and losing `integerDigits`/`decimalDigits`/`zeroSuppression`.

**No settings editor in the admin table** (`admin/panel-templates-table.tsx`) — rebuilding ~60 fields across four CAM-tool tabs in an admin dialog would duplicate that UI and guarantee drift. Staff instead configure the CAM tool itself and click a staff-only **"Publish as Shared"** button in the picker (`POST /api/admin/panel-templates` with the same `extractPanelTemplateSettings()` output the save-as-new flow uses); the admin table only manages rename, the default pick, and deletion of already-published rows.

**Invalidation on apply** (`applyPanelTemplate`, store.ts) follows the same stale-plan discipline as every other config mutator: applying `panel` sets `routingStale: true` and nulls `panelArrayFiles` (no `panelArrayStale` flag exists, so a stale batch-drill file has no banner to warn behind — it must be cleared outright); applying `routing` sets `routingStale: true`; applying `gcode` nulls `gcodeFiles`; applying `array` nulls `panelArrayResult`/`panelArrayFiles`. `panelResult` itself is deliberately never recomputed — the picker shows a hint to click Create Panel instead, matching "nothing auto-computes".

**Known consequence, not a bug**: a loaded template carrying a non-default `panelConfig.drillFormat` suppresses `maybeSyncExportDrillFormat`'s auto-detection on the next drill-file import (`store.ts` — that auto-sync only fires while the config still structurally equals `DEFAULT_DRILL_FORMAT`). This is correct — an explicit template choice should win over a heuristic — but is worth knowing before debugging a "drill format stopped auto-detecting" report.

### Multi-design panelization

A panel can hold **several different board designs**, packed together and ranked by area efficiency — not just N identical copies of one board. This is a generalization of the pre-existing single-design engine (single-design is the N=1 case), not a parallel feature; the fiducial/rib-text/routing machinery documented above is shared, not duplicated. Full staged build history and the original design constraints: see the "Multi-design panelization" plan this was built from (superseded by this section once merged; not kept in-repo).

⚠ **`camMode: 'single' | 'multi'` (store, default `'single'`) is the tool-wide switch that keeps the two workflows apart in the UI.** Real users found the merged tool highly confusing, so the multi-design surfaces are hidden entirely in single mode. What the mode changes:

| | `'single'` | `'multi'` |
|---|---|---|
| Designs tab | hidden (filtered out of `portal-main.tsx`'s tab list) | shown |
| ZIP/RAR import | **appends to the active design** once one exists (`resolveImportDesignId`) | one archive = one design |
| `computePanelResult` | grid path (`computePanel`) | **re-packs** (`findPackCandidates` → `buildPackedPanelResult`) |
| Layers panel | flat list, active design only | grouped by design (color dot + name + Active badge) |
| Export | active design's layers only | every design (the merge below) |
| Panel Config | Rows/Cols + gaps | gaps only; button reads "Re-pack & Rebuild Panel" |

The headline fix is the import row: **every** archive import used to call `createDesignFromArchiveName`, so a user re-importing a revised ZIP of the *same* board silently got two designs — with grid panelization (scoped to `activeDesignId`) panelizing only the newest while both boards' layers showed mixed in the flat Layers list and superimposed in the viewer. Single mode now appends instead; multi mode keeps one-archive-one-design, which is the point of that mode.

`setCamMode` follows the same stale-plan discipline as every other invalidating action: it clears `panelResult`, `routingResult`/`routingStale`/`routingFocus`, `gcodeFiles`, `boardContour`, `panelArrayResult`/`panelArrayFiles`, and `packCandidates`/`selectedCandidateId`/`packInfeasible` (a grid panel is meaningless in multi mode and a packed one in single mode), and resets `activeTab` off `'designs'` when switching to single. It deliberately KEEPS `layers`, `designs`, `activeDesignId` (multi → single is **non-destructive** — other designs stay loaded but hidden until you switch back), `dfmReport` (scoped to the active design, whose geometry the switch doesn't touch), and every config slice. "Clear All" still wipes hidden designs too — scoping it would strand designs with no UI able to remove them, since the Designs tab is hidden in single mode.

⚠ **Multi-mode "rebuild the panel" RE-PACKS; it never re-applies the stored candidate.** Every rebuild call site — Panel Config's button, Info & Export's "Apply Changes to Gerber", and the Routing tab's one-click fixes carrying `rebuildPanel: true` — funnels through `computePanelResult`. A candidate's placements have the gaps BAKED IN (the packer's inflate-then-pack technique) while `validateRouting` measures gap conflicts against `panelConfig.gapX/gapY`, so the routing gap fix (which patches those config gaps then rebuilds) must actually re-run the packer at the new gap — re-applying the stored candidate would leave the "fixed" panel carrying the old too-tight spacing while the pre-flight check reported clean. That's fabrication scrap, not a cosmetic mismatch. The user's layout *choice* is preserved across the re-pack by matching `(strategy, fillOrder)`, never the raw `PackCandidate.id` (whose trailing index shifts as the candidate set changes). Relatedly, `updatePanelConfig` now nulls `packCandidates`/`selectedCandidateId` when `gapX`/`gapY` change — `updateDesign`/`updateMaterialSize` already did, gaps were simply missed.

Before this separation there was a `panelMode: 'grid' | 'pack'` field with a switch card in Panel Config, but `computePanelResult` never read it — "Create Panel" silently replaced a packed panel with a grid one. `panelMode` is **gone**; `PanelResult.source` already records what produced the current panel for anything that needs to know.

**Data model.** `PanelPlacement` (`panelization-engine.ts`) replaces the old `pcbPositions: {x,y,row,col}[]` — `{x, y, w, h, rotationDeg, designId, row?, col?}`, panel-absolute Gerber Y-up mm, `w`/`h` already the bbox AS PLACED (swapped for a 90/270 rotation, though see "Rotation" below — nothing produces a non-zero `rotationDeg` today). `row`/`col` are grid-mode-only and DISPLAY/DEBUG ONLY, never load-bearing — a packed layout's placements never set them. `PanelDesignSummary` (`{designId, name, widthMm, heightMm, count, rotationsDeg}`) is `PanelResult.designs`, used for rib text and READMEs. `PanelResult.source: 'grid' | 'pack'` and `grid?: {rows, cols}` (grid mode only) round out the type. In the store, `DesignEntry` (`{id, name, color, minCount, maxCount, allowRotation, rotationBlockedReason, priority}`) is the user-facing per-design config, and every `LayerEntry` carries `designId: string` (tagged at import — `resolveImportDesignId` decides: a new design per archive in multi mode via `createDesignFromArchiveName`, the active design in single mode via `ensureActiveDesignId`, which loose files always use) plus `variantRotationDeg: 0|90|180|270` (currently always `0` — see "Rotation").

`resolveDesignGeometry<T>(layers)` (`panelization-engine.ts`) is the ONE place that turns a design's own layer set into `{datum, widthMm, heightMm, fromFallback, outlineIsRectangular, hasMacroApertures}` — explicit `outline` layer first, else the largest-area visible layer, matching the exact same priority `computePanelResult`/the exporter/the routing actions all already used before this was unified into one function. Every per-design consumer (grid mode's `computePanelResult`, the packer's `findPackCandidatesAction`, the exporter's per-design datum, G-code/array's drill collectors, routing's per-design outline context) calls this the same way so none of them can silently disagree about where a design's origin is.

**Packing engine** (`src/lib/packing/`, pure — zero React/store/tracespace imports, same discipline as `routing/geometry.ts`). Given several `PackItemSpec`s (design + min/max count + rotation allowance + priority) and a max material size, `findPackCandidates` returns several ranked `PackCandidate`s. Four strategies (`shelf`/NFDH, `guillotine`/best-area-fit, `maxrects`/best-short-side-fit, `block-grid`/per-design sub-grids — the last one reproduces today's uniform lattice exactly at N=1) × five fill orders (`min-only`, `area-desc`, `area-asc`, `ratio-balanced`, `priority-then-area`) × rotation policy, enumerated and deduped (exact signature, then near-signature) down to the top 8 by efficiency → totalBoards → panel area → id. Gaps are honored via "inflate-then-pack": every item is inflated by `(gapX, gapY)` before packing into an inflated bin, so two non-overlapping inflated rects are provably separated by ≥gap on at least one axis — the same contract the routing engine's own gap math depends on. Deterministic (no `Math.random`) so a selected candidate reproduces exactly on re-run. `finishPackedPanel` (`panelization-engine.ts`) then runs the SAME `finishPanel` pipeline grid mode uses (tooling holes, fiducials, rib text — every fiducial/rib-text section documented above applies unchanged) keyed by `source: 'pack'`; `gridWidth`/`gridHeight` for that pipeline are derived from the placements' own bbox rather than the `rows×cols` formula, which is mathematically identical for a uniform grid (proven, then verified byte-identical against the golden corpus) and the only way to support a non-uniform packed layout at all.

**Per-design store scoping.** `alignDrillLayersToBoard`, `rotateAllLayers`, `rebuildBoardView`, `runDfmCheck`, `computePanelResult`, `generateRouting`, `generateGcodeFilesAction`, `generatePanelArrayFilesAction` all filter to the relevant design(s) rather than operating on the whole unscoped `layers` array — grid-mode single-panel actions scope to `activeDesignId`, while export/routing/G-code (which must handle every design actually present in `panelResult`) scope to `panelResult.designs`. `packCandidates`/`selectedCandidateId` are nulled everywhere `panelResult` is nulled, plus on any design add/remove/min/max/rotation/material-size change AND on a `gapX`/`gapY` change or a `setCamMode` switch — a stale candidate list must never be applicable to geometry that's moved on.

**The single-PCB viewer views scope to `activeDesignId` in BOTH modes.** `visibleLayers` (and `boardModeLayers` derived from it, plus `combinedBounds`' fallback and the "N/M layers" status readout) filter by design; the hover-isolation branch deliberately does not, so hovering any Layers-panel row still isolates that layer. This is a fix, not just mode plumbing: `rebuildBoardView` has always been active-design-scoped, so the previously-unscoped overlay drew a second design's artwork over the *first* design's substrate at unrelated native coordinates. The whole-panel paths (`boardModeLayersByDesign`/`visibleLayersByDesign`) stay unscoped — a packed panel legitimately shows every design at once, each at its own placements.

⚠ **`exportPanelizedGerbers` drops drill layers belonging to designs with ZERO placements** on this panel. Without it, such a design still folds its tool diameters into the Excellon tool table and emits one dangling bare `Tnn` line per flash (`generatePanelizedDrill` pushes the T-code before looping the empty position list). Reachable today with a 0-count packed design; routine once single mode's hidden designs exist. The Gerber merge path already skipped zero-placement designs — this brings the drill path in line, and is byte-identical for every single-design export (whose one design always has placements).

⚠ **`computePanelResult` (grid mode) must remap `computePanel`'s placement/design `designId` from its internal `SINGLE_DESIGN_ID` sentinel to the REAL active design's id** — `computePanel`'s pre-multi-design 4-arg signature has no way to know the real id, so it always stamps the sentinel. Every per-design lookup downstream (`boardViewsByDesign`, `generateMergedPanelizedGerber`'s contributor matching, routing's per-design context) is keyed by REAL design ids, so a panel still carrying the sentinel silently matches none of them. Confirmed live: with 2+ designs loaded, clicking "Create Panel" (or any Routing-tab one-click fix with `rebuildPanel: true`) produced a correctly-SIZED panel that rendered as bare, contentless rectangles — the geometry was right, the content lookup just found nothing. Fixed by remapping `result.placements[].designId`/`result.designs[].designId` to `activeDesignId` immediately after the `computePanel` call, before anything reads them.

**Viewer rendering** (`gerber-viewer.tsx`, Board view). `boardViewsByDesign: Record<designId, BoardView>` (store) holds one composited board per design — `rebuildBoardView` builds the active design's own `boardView` (unchanged field, still drives non-panel views) AND, in parallel, every OTHER design's own composite from that design's own layers. The panel-view rendering (both the Board-view `<defs>`/`<use>` path and the per-layer overlay fallback) groups `panel.placements` by `designId` and, per placement, pulls that placement's OWN design's layer set, mask-pair table, and reference bounds (`designRefBounds`) — never the active design's. Single-design output is DOM-structurally unchanged (verified) since a single-design panel's placements all share one `designId` anyway.

**Export merge + D-code/macro remap** (`gerber-exporter.ts`/`panelization-engine.ts`). Two designs sharing a panel each contributing e.g. a "Top_Copper" layer merge into ONE output file — that's the point of panelizing them together. The merge key is the exact output filename fragment (`generateDescriptiveLayerName`), which deliberately mirrors the SAME collision behavior a single design with two layers of that type/side already had (e.g. two inner-copper layers both classifying `side: 'none'`): whichever `LayerFile` comes last in array order wins that design's contribution to the merge group — real multi-layer stackups aren't disambiguated (no stackup checking is in scope), only surfaced via a `console.warn`.

`generateMergedPanelizedGerber` (`panelization-engine.ts`) takes an ordered list of `GerberExportContributor`s (one per contributing design, in `panel.designs` order — store design order) and:
- **Contributor 0 is never touched** — identity D-codes, identity `%AM` macro names, identity apertures/commands.
- **Contributor k≥1 is remapped**: its D-codes are renumbered in ascending old-code order continuing a SHARED cursor across all contributors (so contributor 2's codes never collide with contributor 1's remapped ones either), and a colliding `%AM` macro name is renamed to `${name}_${k}` — never an attempt to prove two identically-named macro bodies are equivalent, since a wrong "these are the same" guess costs boards where a renamed duplicate only costs bytes.
- **Byte-identity for the single-contributor case is STRUCTURAL**: with exactly one contributor, the function delegates straight to the unmodified `generatePanelizedGerber` (which gained a `placementsOverride` parameter, defaulting to `panel.placements`, purely additive for every pre-existing call site) — so single-design output can never drift from that function's own evolution.
- **L-shape marks are per-contributor** (own `w`/`h`, own outline-rectangular eligibility via `effectiveConfig.enableLShapeMarks`) so a rectangular design sharing a file with a shaped one doesn't lose its own marks; donuts/fiducials/rib text remain panel-wide, emitted once using the merged overlay code space (allocated above every contributor's own codes).

Verified with the "killer fixture" the plan called for: the SAME real Gerber file set imported twice as design A and B (identical `%AM` names, identical D-codes — the maximally adversarial case) produces zero duplicate `%ADD` codes, zero duplicate `%AM` names, and every `D<n>*` selection resolves to a real aperture. `generatePanelizedDrill`/`collectPanelizedDrillHoles`/`collectPanelizedDrillSlots` gained an analogous `perDesignBaseOffset`/per-design-placements-filter path (also purely additive, defaulting to the old global-offset/all-placements behavior) so a multi-design panel's drill file stamps each design's own drill hits only at that design's own placements. `generateGcodeFilesAction`/`generatePanelArrayFilesAction` had the SAME single-design-only drill collection bug `computePanelResult` had (scoped to `activeDesignId`, silently stamping one design's holes across the whole panel) — fixed via `collectAllDesignsDrillHoles`/`collectAllDesignsDrillSlots` (`store.ts`), which run the existing collector once per design against a placements-filtered sub-panel and merge by diameter.

**Per-design routing** (`plan-routing.ts`). `RoutingPlanContext` gained `designs?: Record<designId, DesignRoutingContext>` (`{outlineLayer, boardContour, outlineBoundsMm}`) alongside its original singular fields, which now serve as the fallback when a design has no entry in the map — every pre-existing single-design caller (nothing sets `designs`) is therefore byte-identical. `planRouting` groups `panel.placements` by design, resolves each design's own outline mode (`resolveOutlineMode`, per design — a rectangular design next to a shaped one can legitimately resolve differently), and:
- **Bbox-mode designs already needed no further generalization** — the bbox loop has read `pos.w`/`pos.h`/`pos.x`/`pos.y` straight off each placement since the Stage 1 `PanelPlacement` migration, never a panel-wide "the" board size. It was extracted into `runBboxModeRouting`, parameterized over an explicit `{pos, pcbIndex}[]` list (preserving each placement's original GLOBAL index as `pcbIndex`, so a true single-design panel's output is unchanged) instead of iterating `panel.placements.entries()` directly, so `planRouting` can hand it just the bbox-resolved subset.
- **Contour-mode designs** run through `runContourModeRouting`, which computes ONE `ContourGeometry` per contour-resolving design (validating that design's own traced `BoardContour` — failure/ambiguous-nesting/multiple-outer-boundary checks are now per design, naming the design in the message when 2+ designs are present) and instances it across only that design's own placements, using that design's own `outlineBoundsMm` datum. Cross-design tab-destruction protection is computed over the GLOBAL set of contour instances (every placement of every contour-resolving design at once, not siloed per design) — a design A board's tab must not be cut through by a neighbouring design B board's pass at a shared gap, and this only works if the coincidence check can see every candidate neighbour regardless of which design it belongs to. Verified with a real two-design "killer fixture" (same contour geometry, design A + B sharing a gap): zero foreign-pass-through-tab violations.
- ⚠ **Contour-mode designs are processed BEFORE bbox-mode designs** specifically so a MIXED bbox+contour panel gets one-directional cross-mode tab protection: contour tabs already exist in the shared `tabs` array by the time the bbox branch's own foreign-tab-fold-in (which scans the whole `tabs` array) runs. The reverse — a contour pass being protected against a bbox design's tab — is a known, accepted gap for the mixed-mode case specifically (same-mode panels, the overwhelmingly common case, are fully protected either way, since each branch's own internal cross-instance protection doesn't depend on processing order).
- The panel-outline pass, the tooling/reference-hole clearance backstop, and `checkContourSize` (now taking a design's own `pcbWidth`/`pcbHeight` instead of a panel-wide scalar) are otherwise unchanged in spirit — panel-wide checks stay panel-wide, per-design checks became explicitly per-design.
- `generateRouting` (store.ts) traces every design's contour that needs one IN PARALLEL (`Promise.all`, using `panel.designs` — not an ad-hoc `layers` grouping — as the source of truth for which designs actually have placements on this panel) before building the `RoutingPlanContext.designs` map and calling `planRouting` once. The single `boardContour` store field (used only by the viewer's cosmetic contour-outline-rect route-overlay treatment) stays pointed at the ACTIVE design's own trace — other designs' route overlays render as plain lines without that specific cosmetic treatment, a documented, accepted gap distinct from routing correctness itself (which is per-design regardless).

**Rotation is deliberately NOT enabled**, even though the scaffolding exists end-to-end: `LayerEntry.variantRotationDeg`, `DesignEntry.allowRotation`/`rotationBlockedReason`, and the packer's `RotationPolicy = 'none' | 'uniform-per-design'` (which DOES enumerate 0°/90° combinations and can propose a `PackedItem` with `rotationDeg: 90`). The missing piece is real: nothing anywhere MATERIALIZES actually-rotated Gerber geometry for a design placed at a non-zero `rotationDeg` — export/viewer/routing would stamp the design's UNROTATED content at a ROTATED slot, silently wrong, not merely suboptimal. Until real rotation materialization exists, `allowRotation` defaults to `false` for every design, `findPackCandidatesAction` hardcodes `allowRotation: false` into every `PackItemSpec` regardless of the stored flag (belt-and-suspenders against stale state), and the Designs tab's Rotate toggle is disabled in the UI with an explanatory tooltip rather than removed outright — keeping the field and the UI slot visible documents that this is a deferred feature with a real design, not an oversight.

`rotateGerberLayer` (`gerber-parser.ts`) — the function both the eventual `materializeRotatedVariant` action and the CURRENTLY-SHIPPED single-design "Rotate Left/Right" (Layers tab, `store.ts`'s `rotateAllLayers`) already use today — rotates `rectangle`/`obround`/`polygon` apertures via width/height swap + rotation angle, but macro apertures need their own per-macro coordinate layout to rotate correctly, since a macro's shape is arbitrary user-defined primitive code, not a built-in parameterization. Confirmed as a real, user-visible bug on a real board (SMD IC pads read as "merged and malformed" after a Layers-tab rotation): KiCad's `RoundRect` macro — by far the dominant real-world case, every KiCad SMD pad with rounded corners — parameterizes its 4 corners directly as `$2,$3`/`$4,$5`/`$6,$7`/`$8,$9` (x,y pairs, not width/height+angle); every primitive in its `%AM` body (the box polygon, 4 corner circles, 4 edge vector-lines) references only those corner coordinates, so rotating just the 4 pairs rigidly rotates the whole rendered pad. `rotateGerberLayer` now special-cases macro apertures whose name matches `RoundRect` and rotates those 4 pairs (radius `$1`, and any unreferenced trailing `$10` some KiCad versions emit, are left untouched) — verified against a real customer file: the rotated pair values match a plain 90° point rotation exactly, and a right-then-left round-trip restores the original values bit-for-bit. `generateApertureDefinitions` (`panelization-engine.ts`) already serializes macro `%ADD` lines straight from `ap.parameters`, so this propagates through re-export/re-render with no other code path needing changes. **This does NOT generalize to other macro names** — there's no way to know an arbitrary macro's own coordinate-parameter layout without interpreting its `%AM` body, so anything else still falls through unrotated, still the real gap `rotationBlockedReason` exists for.

### UI layout (Panelization tool)

Collapsible resizable sidebar (280–600px) + full-height SVG canvas. Eight sidebar tabs, in display order — **Layers**, **Designs**, **DFM Check**, **Panel Config**, **Routing**, **G-Code**, **Stencil**, **Info & Export** — controlled by `activeTab` in the store, typed as `CamTab` (extract/extend that union rather than re-spelling it inline; it used to be declared twice and could drift). **Designs only renders in `camMode === 'multi'`** — `portal-main.tsx` filters it out of the tab array otherwise, and `setCamMode` bounces `activeTab` back to `'layers'` when switching to single so nobody lands on a hidden tab. The tool-wide **Single Design / Multi-Design** segmented switch lives in the CAM sub-header (not inside any tab — it gates which tabs exist at all, and stays visible with the sidebar collapsed); see the multi-design section above for the full behavioral table and `setCamMode`'s invalidation list. Which tabs show the whole *panel* rather than the single PCB is `PANEL_VIEW_TABS` / `isPanelViewTab()` in `store.ts` — `gerber-viewer.tsx` gates SIX separate things on it (bounds, the panel-overlay memo, the route overlay memo, both `<use>`-repeat render paths, the status readout) and they must all agree, so never re-spell it as an `||` chain at a call site. Panel computation is only triggered by explicit user action (clicking "Create Panel"), not automatically on layer add or config change; the DFM check ("Run check"), routing ("Generate Routing"), G-code ("Generate G-Code"), and the stencil DXF ("Generate Stencil") all follow the same convention.

⚠ **The route overlay (`routeOverlayContent`) was originally exempted from this gating on purpose** ("stays visible while you look at other tabs") — that design was disproven live: `routingResult.paths` are always PANEL-ABSOLUTE coordinates, but the single-PCB view a non-panel tab (Layers, DFM Check) renders is drawn in that board's own NATIVE file coordinates with no panel-position offset applied. The two frames only coincide by coincidence, so a generated routing plan showed as a giant panel-shaped path floating arbitrarily far from the one small board on screen — reported by the user as "routing path generated -> clicked on Layers Tab". Fixed by adding `isPanelViewTab(activeTab)` to `routeOverlayContent`'s guard and dependency array, same as `panelOverlayContent` — this is the sixth thing gated on it.

### Stencil DXF export (SMD paste-stencil laser cutting)

`src/lib/stencil-geometry.ts` + `stencil-dxf.ts` + `stencil-types.ts` export a DXF of the solder-paste apertures for laser-cutting a stencil on 0.15/0.25mm Mylar, per-side (top/bottom checkboxes, each side its own file), scoped to either the active design (single-PCB) or tiled across the whole computed panel, with an optional area-based reduction% (fine-pitch bridging prevention) and an optional board/panel outline riding along as a scribe-line layer. No fiducials — explicitly out of scope.

**Macro apertures (KiCad RoundRect etc.) are resolved via the tracespace plot tree, same precedent as `dfm/capsules.ts`'s copper-clearance check** — this codebase's own parser never resolves a macro aperture into concrete geometry (the same gap `rotateGerberLayer`'s RoundRect-only special case exists for), but `plot()` already has, since it must render the shape. `extractStencilApertures` (new Comlink method on `gerber-worker.ts`, alongside `checkCopperSpacing`, same parse→plot→`scalePlotTreeToMm` preamble) walks the plot tree's children (one per flash, absolute coordinates, a macro flash arriving as one `layeredShape` bundling its sub-primitives) and — rather than `capsules.ts`'s boundary-segment/capsule representation, which is fine for distance checks but not a filled cutout — samples every sub-primitive's boundary into points and takes their **convex hull** as the aperture outline. This is exact for any convex pad shape (rect, roundrect, circle, obround — effectively every real paste aperture) with no polygon-union math or new dependency, at the cost of slightly over-cutting a hypothetical non-convex custom paste polygon — a deliberate tradeoff, confirmed with the user, over pulling in a clipping library. `capsules.ts` exports its `ARC_TOLERANCE_MM`/`MAX_ARC_SEGMENTS` constants (previously private) so both files flatten arcs to the same tolerance rather than each defining their own.

Reduction is an **area-based** centered scale — `k = sqrt(1 - pct/100)` applied to every hull point around the hull's own bounding-box center (each aperture shrinks around its own center, not the board's) — so a 20% reduction is a linear scale of ≈0.894, not 0.8; verified against a plain-rectangle pad that a 20% reduction leaves exactly 80% of the original area.

Whole-panel tiling (`tileAperturesAcrossPlacements`/`translateRings` in `stencil-geometry.ts`) mirrors `generatePanelizedGerber`'s own per-placement translation (`dx = pos.x + datum.x`) using the same `resolveDesignGeometry` datum every other export/tiling consumer uses — no rotation math needed, since `PanelPlacement.rotationDeg` is never non-zero anywhere in this codebase today (rotated-variant materialization is the same deliberately-unshipped feature documented in the multi-design rotation section above). The board/panel outline scribe line reuses `traceBoardContour` exactly as routing's contour mode does (`ContourRing.points`, already-closed, arc-flattened, Gerber-native mm) — including passing a real `unionBoundsMm` (union of every imported layer's own bounds, computed the identical way `generateRouting` does) rather than `null`, since `boardShapeCoversContent`'s outline-trust gate (`board-contour.ts`) unconditionally rejects a null union and silently produces zero scribe-line rings otherwise — caught live (a generated DXF had the OUTLINE layer defined in its DXF `LAYER` table but zero polylines on it) before being fixed.

Store wiring follows the routing/G-code precedent closely: a flat `StencilConfig` (`scope: 'single'|'panel'`, `includeTopPaste`/`includeBottomPaste`, `reductionPct`, `includeOutline`), `stencilFiles: StencilFile[] | null` nulled at the same layer/panel/design-mutating call sites `gcodeFiles`/`panelArrayFiles` are (no separate `stencilStale` flag — regenerating is one click and cheap, matching the `panelArrayFiles` precedent) but deliberately **not** nulled by routing- or G-code-specific regeneration (stencil geometry depends on neither). `generateStencilFilesAction` is the one place besides `export-panel.tsx`'s own `camMode==='single' && activeDesignId` filter that needs an explicit user-facing single-PCB/whole-panel scope choice — routing/G-code are always panel-scoped to `panel.designs`. `exportStencilFiles` (`gerber-exporter.ts`) is a standalone ZIP (own `stencil/` folder, own README, `_Stencil.zip` suffix) — copies the exact `JSZip`/`saveAs` shape `exportGcodeFiles`/`exportRoutingFiles` already use, filenames baked with the sanitized part number at generation time (matching `GcodeFile.filename`'s own convention, not deferred to export time).

DXF output is **R12 ASCII** (`POLYLINE`/`VERTEX`/`SEQEND`, `$INSUNITS`=4 for mm) rather than the newer `LWPOLYLINE` (R14+) — the oldest, most universally-parsed entity form, chosen for compatibility with cheap Chinese laser-cutter software rather than modern CAD tooling.

**Canvas preview** (`src/components/stencil-preview-canvas.tsx`), added after the initial download-only ship per direct user request ("just like multi panel array preview in canvas"), swapped in for the normal Gerber/panel viewer while the Stencil tab is active (`portal-main.tsx`'s `activeTab === 'gcode' ? <ArrayLayoutCanvas/> : activeTab === 'stencil' ? <StencilPreviewCanvas/> : <GerberViewer/>`), the same Y-up→Y-down flip-transform trick as `array-layout-canvas.tsx`. The drawn CONTENT only reflects the last `Generate Stencil` click (nothing auto-computes on toggle changes, same convention as everywhere else in this tool) — it reads a `stencilPreview` store field, geometry kept separate from `stencilFiles` (the serialized DXF text) the same way `panelArrayResult` is kept separate from `panelArrayFiles`, so the preview doesn't need to re-parse DXF output to render. The VIEW (zoom/pan/fit) is fully interactive on top of that static geometry, per a direct follow-up request — scroll wheel to zoom around the cursor, Alt+drag or middle-click to pan, double-click to re-fit, +/-/⊞ buttons, exact same transform math and interaction model as `gerber-viewer.tsx`'s `handleWheel`/`handleMouseMove`/`doZoom` (copied, not reinvented), just seeded from this preview's own ring bounds instead of layer bounds.

⚠ **The wheel-zoom listener must depend on the empty/loading state, not just `handleWheel`.** Unlike `gerber-viewer.tsx`, which always renders one persistent `<svg>` (empty states are drawn as overlay text on top of it), this component's loading/no-preview/nothing-to-preview states are separate early `return`s that render an entirely different tree with no `<svg>` at all — so the real `<svg>` node unmounts and remounts across a generating→populated transition. The native `addEventListener('wheel', ...)` effect was originally keyed only on `[handleWheel]` (mirroring gerber-viewer.tsx literally), which is correct THERE because that `<svg>` never unmounts — but here, `handleWheel`'s own identity doesn't necessarily change across that transition (its deps are `containerSize`/`parseViewBox`, unrelated to mount state), so the effect skipped re-running and left the listener attached to the stale, already-unmounted previous node. Symptom confirmed live: wheel-zoom did nothing after the very first Generate, while the +/-/fit buttons (plain React `onClick`, no native-listener/ref timing involved) worked fine — the give-away that isolated it to the listener-attachment effect specifically, not the zoom math. Fixed by adding `stencilGenerating`, `stencilPreview`, and `bounds` to that effect's dependency array so it re-attaches every time the `<svg>` itself (re)mounts.

`FlashAperture` (`stencil-geometry.ts`) carries both `hull` (the actual cut geometry — reduced, if a reduction% was requested) and `originalHull` (the same hull *before* reduction, computed once per flash and threaded through unchanged rather than re-extracted). The worker's `StencilApertureOutput` and `generateStencilFilesAction` both propagate `originalHull` alongside `hull` so the preview can show the true pad shape and the actual cut side by side without a second extraction pass. The canvas draws three tiers, back to front: the outline scribe line (neutral gray-blue, dashed, no fill), the original pad outline (amber, dashed, light fill — **only rendered when `reductionPct > 0`**, since at 0% `originalHull`/`hull` are the same array by reference and drawing both would just double-paint an identical polygon), then the reduced/actual-cut geometry on top (cyan, solid fill) — the most prominent layer, since that's what actually gets laser-cut. Verified live: at 20% reduction, exactly 12 amber + 12 cyan aperture polygons (2 pads × 6 panel placements) plus 6 gray outline polygons render with the expected stroke/fill attributes; at 0% reduction the amber layer disappears entirely and only 12 cyan + 6 gray remain.
