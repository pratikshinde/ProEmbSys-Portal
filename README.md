# ProPCB / ProEmbSys Portal

A PCB manufacturing portal for ProEmbSys Technologies — customer-facing quoting, ordering, and account management backed by PostgreSQL, plus a fully client-side Gerber/Excellon panelization tool.

This file tracks **what exists and what's been done**. For setup instructions see [SETUP_GUIDE.md](SETUP_GUIDE.md); for architecture, data flow, and implementation gotchas see [CLAUDE.md](CLAUDE.md) (kept in sync with the codebase — the authoritative technical reference).

## What's here

- **Marketing site + Panelization tool** (`portal-main.tsx`) — Home, PCB Order (quoting), CAM Panelization, Assembly, Shop, Blog. Client-side page switcher, URL-synced.
- **Real backend** (App Router + Prisma + PostgreSQL) — auth, admin-editable pricing, orders, customer↔staff messaging, account/address book, staff management, blog/shop/testimonials CMS.
- **Gerber/Excellon engine** (`src/lib/gerber-parser.ts`, `panelization-engine.ts`, `gerber-exporter.ts`) — custom RS-274X + Excellon parsers, panel layout math, RS-274X/Excellon export, film-plot PDF rendering. No external services; rendering runs in a Web Worker via `@tracespace`.
- **CAM job library + sharing** — save/reload CAM tool sessions with workflow status and derived health, email role-specific output bundles (film/drill/test) to saved contacts via expiring per-recipient links, and staff visibility into jobs the customer has linked to an order or shared with the team.

## Status

Actively developed. Core ordering flow, backend, and panelization tool are functional end-to-end and manually verified in-browser after each change (see progress log below). No automated test suite yet.

### 2026-08-24 — Surface parser and export D-code/aperture warnings to the user
- **Import**: the Gerber parser already collected a rich warnings list (undefined aperture selected, unclosed regions, un-expanded step-and-repeat, unusual zero-suppression, …) but it was parsed and discarded — nothing ever showed it. `actionableParseWarnings()` filters out the one routine "macro defined" note and surfaces the rest through the existing ZIP/RAR import-result panel (now also used for loose single/multi-file imports, not just archives) as a distinct warnings section — exactly the "new construct from unfamiliar CAD software" signal that would have flagged the very next entry's octagon-macro bug at import time instead of only surfacing later as a missing pad on export.

### 2026-08-24 — Fix macro aperture pads (EAGLE octagons, KiCad RoundRect) rendering 25.4x too small after unit conversion
- **`convertLayerUnits()` scaled `width`/`height`/`holeDiameter` on an inch↔mm conversion but never touched a macro aperture's own `$N` modifier values**, which carry a macro shape's actual size. A real EAGLE export's octagon pad macro (`OC8`) stayed at its original `0.052in` modifier while the file was re-declared metric — shipping every octagon pad 25.4× too small in the exported Gerber. Invisible in Delta Gerber Viewer, though both the untouched original file and this tool's own canvas preview (which bypass the converted layer) rendered fine — exactly the kind of "looks right here, wrong everywhere else" bug that's easy to miss without checking the actual exported bytes.
- Fixed by scaling macro modifier values during the same unit-conversion pass, for both EAGLE-style octagon macros and KiCad's `RoundRect` (which parameterizes size via corner coordinates rather than width/height, needing its own scaling path).
- Verified against the real reporting file: re-exported octagon pads now measure correctly at native size; `tsc` clean.

### 2026-08-24 — Fix EAGLE octagon-pad macro (uppercase `X` operator) dropped by strict Gerber parsers on export
- **User reported octagonal pads (EAGLE's standard THT/SMD pad shape, an `%AMOC8*%` macro aperture) visible in this tool's own preview but missing from the exported Gerber**, on the same real `2270.zip` file from the previous fix. Ruled out this codebase's own export text generation first — a headless parse → panelize → export → re-parse round trip against the real file (both the single-design path and, since the reporting workflow used a multi-design panel, the harder `generateMergedPanelizedGerber` "same macro name across two designs" case) came back completely clean: macro body copied correctly, all `%ADD` references present, zero flashes referencing an undefined aperture, exact expected flash counts on re-parse. The exported text is complete and self-consistent by every check this codebase can run against itself.
- **Root cause was one character, in the source file, silently propagated through**: the macro's diameter parameter is a parametric expression, `1.08239X$1` (constant × the aperture's own scale parameter) — using an **uppercase `X`** for multiply. The Gerber Format Specification requires **lowercase `x`** and explicitly calls out uppercase X as something to avoid, since it's easily confused with coordinate data. Lenient parsers (tracespace, this tool's own preview) accept either case; a stricter downstream Gerber parser rejects the malformed expression and drops the primitive entirely — exactly "renders here, missing wherever the user checked the actual exported file." Confirmed byte-exact in the real file's macro block (`5,1,8,0,0,1.08239X$1,22.5*`) — EAGLE 7.x is a known source of this specific non-compliance.
- Since this codebase copies macro bodies through **verbatim** from the uploaded file (`extractMacroDefinitions`, by design — it doesn't re-derive macro geometry, just passes the original text through for re-export), the defect passed straight into every exported file untouched.
- Fixed by normalizing macro arithmetic operator case at the same extraction point already used by both export paths — lowercases every `X` within a macro's primitive *body* (never its name, and never an `%ADD` aperture body, where `X` is legitimately the width/height separator — a completely different grammar this function doesn't touch). Verified: exported macro body now reads `1.08239x$1`; re-parsed flash count unchanged (24, no regression); macro name (`AMOC8`) untouched.

### 2026-08-23 — Fix EAGLE `.ssm` soldermask files being dropped/misclassified ("mask not rendered")
- **User reported soldermask not rendering on a real EAGLE CAM Processor export** (`2270.zip`): the Board view showed copper painting flat, with none of the gold pad-finish reveal soldermask normally shows. Traced to two stacked gaps in the filename-heuristic layer classification (this file has zero `TF.FileFunction` Gerber X2 attributes — EAGLE 7.6.0's CAM Processor emits none — so classification depends entirely on the filename).
- **Gap 1**: the ZIP-import extension allowlist (a regex duplicated in two places in `store.ts`) recognizes EAGLE's `.sol` (bottom copper) and PADS-style `.smb`/`.smt`/`.ssb`/`.sst` soldermask/silk extensions, but not EAGLE's own `.ssm` (Solder Side Mask) — the file was silently dropped at import, before classification even ran. "Imported 2 of 2 layers" showed no error, since the drop-detection only fires when *nothing* in an archive matches, not when some files match and others don't (the same class of gap `.ssb`/`.drd` had before an earlier fix).
- **Gap 2**: even past import, `detectLayerType`/`detectLayerSide` (`gerber-analysis.ts`) had no `.ssm` handling either and would have fallen through every heuristic to `'other'` — which the Board view compositor excludes entirely, so `getMaskClipPairs` never finds a mask+copper pairing for the design and copper paints flat with no soldermask tint or gold reveal at all.
- Fixed both: added `.ssm` to the import allowlist and to `detectLayerType`/`detectLayerSide` (classified as `mask`/`bottom`, matching the `.sol`→`copper`/`bottom` pair already handled). Added `.csm`/`.tsm` (the top-side counterpart in the same EAGLE naming family) defensively at the same time, though not directly evidenced by this file — it's single-sided, bottom-only, so no top-mask file existed to confirm the exact top extension this particular CAM job template uses.
- Verified end-to-end against the real file: re-imported after the fix and confirmed "Imported 3 of 3 layers" (previously 2 of 3, with the mask file silently missing), the layer now shows as "Bottom Mask (B.Mask, GBS)", and the rendered Board view SVG gained a real `<mask>` element plus the documented `#d4af37` pad-finish gold color — the exact reveal-through-mask compositing that was absent before.

### 2026-08-19 — Mirror drilling for copper-up CNC drilling of single-sided boards
- **New feature, requested for single-sided PCBs**: a single-sided board is drilled with copper facing UP on the CNC — the panel is physically flipped over first, so every hole's X position needs to mirror within the panel to match. Previously there was no way to get a drilling program in that orientation without hand-editing the output.
- Added `mirrorX` (default off) to both the meta-panel array config and the plain G-Code tab's `GcodeContext` — deliberately two independent flags, since a job might batch-drill an array without touching the ordinary single-panel program, or vice versa. Both reuse the same pure mirror primitives (`mirrorHoleGroupsForArray`/`mirrorSlotGroupsForArray`, `panel-array.ts`) — a straight X reflection about the panel's own (rotation-adjusted, for the array case) width, applied to the collected hole/slot groups right before the drilling program is built.
- **Drilling-only, deliberately**: the cutting/routing program is a separate physical setup step and is never mirrored — the UI labels this explicitly ("Mirror drilling (copper-up drilling)"), and the meta-panel array's border marks (which the operator registers the panel's physical corners against) are mathematically unchanged by the mirror either way, since a rectangle's 4-corner L-mark set maps onto itself under reflection.
- The meta-panel array's generated file bundle now carries its own `mirroredX` flag, surfaced both in the file-list UI (a small warning-colored note next to "Files") and in the exported README ("*** DRILLING IS MIRRORED (copper-up) ***") — the border-mark Gerber is byte-identical whether or not drilling is mirrored, so nothing in the file list itself would otherwise tell an operator which program they're holding, a real scrap risk if the note weren't there.
- Also closed a config-invalidation gap found while wiring this up: editing the meta-panel array config or the G-Code context previously left an already-generated file bundle sitting stale and downloadable — neither `updatePanelArrayConfig` nor `updateGcodeContext` cleared anything. Both now drop their generated-files bundle on any edit, matching the invalidation discipline `updatePanelConfig` already established elsewhere.
- Added `mirrorX` to both the `array` and `gcode` sections of the panel-template zod schema — an omission there silently strips the field on template save/load.
- **Verified with a live differential test against the real reporting customer's file**: generated the same drilling program with the flag off and on, extracted both from the actual downloaded ZIPs, and matched all 72 holes between the two — every hole's Y unchanged, X exactly equal to `panelWidth − x` (panel width 209.882mm) to within 0.01mm, a 100% bijective match. Also caught and fixed a test-harness mistake along the way (a mis-targeted click had toggled "Auto feed by diameter" off instead of the mirror switch, surfaced immediately by a feed-rate mismatch between the two captures) before it could be mistaken for a real bug.

### 2026-08-19 — Make the per-design mirror consistent across every file-producing output
- **The export-only mirror (previous entry) was incomplete**: it materialized a real geometric mirror for the panelized Gerber/Excellon export, but routing, G-code, stencil, and the meta-panel array all still read the unmirrored store layers — so a mirrored export's drill holes, tool paths, and stencil apertures would silently disagree with the mirrored copper/mask/silk. A real fabrication-registration risk, not just a display quirk.
- Considered and rejected materializing the mirror directly into the store (mutating `parsedLayer` in place, `rotateAllLayers`-style): it breaks CAM-job save/restore into an unrecoverable state (jobs persist the pristine `originalContent`, not the mirrored `rawContent`, so a reloaded job would show `mirrorBottomOverride: true` next to geometry that was never actually mirrored), mutates live state with no rollback on failure, silently leaves a later-imported layer in the opposite handedness from the rest of its own design, and turns what's meant to be a cheap diagnostic toggle into an action that wipes the computed panel/routing/G-code/stencil on every click.
- **Fix: one shared derivation point instead.** New `getMirroredLayers()` (`src/lib/design-mirror.ts`) clones and mirrors a flagged design's `parsedLayer` on demand, per consumer, leaving the store untouched — wired into the panelized Gerber export, G-Code tab generation, the meta-panel array, and (via the companion `mirrorRingsX`/`mirrorBoardContourX` helpers, since routing's contour trace and the stencil's paste-aperture hulls both come from the worker over raw file text rather than `parsedLayer`) routing's contour-mode board profile and the stencil's aperture/outline geometry. DFM and panel-layout sizing are deliberately *not* wired in — DFM measurements are all distances, and a reflection is an isometry, so results are identical either way.
- **Refuses to mirror a design with real top-side geometry**, warning instead of silently flipping a genuinely two-sided board's top artwork along with the bottom (the override only makes sense for a design stored entirely in the legacy bottom-view convention).
- **Two real bugs found and fixed in `mirrorGerberLayerX` itself while wiring this up**, both of which also affected `rotateGerberLayer` and were fixed there too: drilled/milled slots (`GerberLayer.drillSlots`, tracked outside `commands`) were never mirrored or rotated at all, and bounds recomputation ignored them entirely (`calculateBounds` → `expandBoundsForSlots`). Also fixed: polygon-aperture rotation used the rectangle/obround formula (`-rotation`), which is only correct for an even vertex count — an odd-sided polygon (triangle, pentagon, ...) needs the real `180 - rotation` reflection. A custom aperture macro other than KiCad's `RoundRect` (the only shape this codebase knows how to mirror the *outline* of) now reports a warning instead of silently shipping a pad whose position is mirrored but whose shape isn't.
- Verified via a headless parse → mirror → re-parse check against the real reporting customer's file (confirming every layer of a design mirrors around the exact same axis, so pad-to-hole registration is preserved by construction) and a live pass exercising all five consumers together with the toggle on: export, routing (including the contour-mode trace this board actually took), G-code, the meta-panel array, and the stencil DXF — all generated cleanly with matching geometry and zero console errors.

### 2026-08-19 — Three real Gerber export bugs found chasing a "mirror broke my panel" report, none of which were actually about mirroring
- **The reported "copper shows only 1 of 3 boards" bug was Gerber polarity, not mirroring.** `generateBodyFromCommands` (the function that replays one panel copy's commands into the output) declared `let lastPolarity = 'dark'` fresh on every call, but never emitted a corrective `%LPD*%` on exit. The reporting customer's copper ends on a clear-polarity run (a thermal relief cutout) — so the emitted file was left in `%LPC*%` while the *next* copy's tracker wrongly assumed dark, silently drawing that entire copy (and copy 3, and every panel-wide overlay appended afterward) in **erase mode**. Confirmed on the real exported file: `%LPD*%`, then three `%LPC*%` in a row with zero dark resets in between. Fixed with a polarity-restoring epilogue mirroring the function's existing region-close epilogue, plus splitting the region open/close around the polarity check so `%LP` is never emitted inside an open `G36…G37` region statement (a real, if rarer, second way the same class of bug could occur). Byte-identical for every layer whose last drawing command is already dark — the overwhelming majority of real files.
- **Fixing that bug exposed a second, pre-existing one it had been hiding: `G74` (single-quadrant) arcs were never disambiguated.** RS-274X's single-quadrant mode stores an arc's center offset (`I`/`J`) as an *unsigned magnitude* — the true signed offset is one of 4 candidates, resolved by which one keeps the start and end points equidistant from the center *and* sweeps ≤90°. This codebase's parser copied the raw unsigned magnitude straight through with no disambiguation, while the exporter always declares `G75` (multi-quadrant, signed `I`/`J`) around it — so a real viewer solves for the wrong candidate and draws a mathematically inconsistent, visibly distorted circle. Confirmed on the reporting customer's file (which opens with `G74*`): the naive reading of the first arc gives mismatched start/end radii (944.1 vs 924.0mm-units); the correctly disambiguated reading matches exactly (944.1 vs 944.0). All 129 arcs in the file were affected — the visible symptom was every rounded silkscreen/copper shape (fillets, capacitor rounds) rendering warped. Fixed by tracking `G74`/`G75` mode during parsing and resolving single-quadrant arcs to the canonical signed form once, at parse time, so nothing downstream needs to know the source file ever used `G74`.
- **A third, independent bug was still hiding underneath both of the above: the D-code selection regex only matched 1–2 digit aperture codes.** `/D(\d{1,2})\s*$/` silently failed to match any 3+-digit aperture selection (`D100` and up) — completely valid and common in real files with more than ~90 distinct apertures. Every such selection fell through to the "no D-code present" branch and inherited whichever 2-digit aperture was last correctly recognized, instead of the actually-intended one. Confirmed on the reporting customer's mask layer (546 defined apertures, real selections up to `D555`): before the fix, only 3 of those apertures were ever actually referenced by the exported geometry (95% of flashes collapsed onto one circular aperture) — exactly the reported "all D-codes look the same." After the fix: 28 distinct apertures on mask, 40 on copper (up from 16 — this one silently affected copper too, just less visibly), 4 on silk. Fixed by widening the regex to `D(\d+)` with no cap, matching the RS-274X spec.
- All three were only reachable/visible in that order — the polarity bug hid the invisible copies from the arc bug, and the arc bug's warped-but-present geometry partly hid how few distinct apertures were actually rendering. Verified end-to-end via a headless parse → panelize (1×3) → export → re-parse round trip against the real reporting customer's file after each fix: 0 of 387 arcs geometrically inconsistent, correct 3× command-count triplication on every layer, and the customer confirmed the final export renders correctly (varied pad shapes, no distortion, no missing boards) in a third-party Gerber viewer.

### 2026-08-18 — Materialize "Fix mirror" into actual exported geometry, not just the preview
- **User reported the previous preview-only mirror fix didn't resolve the real problem**: even after fixing the panel-view rendering bug (below), the exported panelized Gerbers of a mirrored design still looked wrong when opened in Delta Gerber Viewer (a neutral third-party viewer with no side-aware auto-flip) — screenshots showed backward-reading text ("GT Swathi : WLC Economy" mirrored) and copper content only visible on part of the panel.
- **Root cause, found via forensic byte-level analysis of the exported ZIP**: the per-design "Fix mirror" toggle was designed as PREVIEW-ONLY on purpose — it's a pure SVG transform that corrects the on-screen display for a legacy file whose bottom-side layers are already stored bottom-view-correct (pre-mirrored), rather than in the standard top-down convention this tool otherwise assumes. That design was right for files that already match the standard convention, but wrong for the case the toggle exists to diagnose: for a genuinely legacy pre-mirrored file, the RAW exported data itself needs the correction, and shipping it unmirrored (as the exporter always did) produces backward fabrication output — confirmed by extracting and parsing the real exported Gerber files directly (correct panel dimensions, correctly-tripled pad content, no corruption — the numbers were right, the orientation wasn't).
- **Fix**: new `mirrorGerberLayerX()` in `gerber-parser.ts` (mirrors every command's X coordinate, flips arc winding direction cw↔ccw since a reflection reverses rotation sense, and mirrors KiCad `RoundRect` macro corners — same shape/precedent as the existing `rotateGerberLayer`). `export-panel.tsx`'s export handler now clones and mirrors a design's `parsedLayer` around that design's own local bounds center — the same reference point the panel-view rendering fix (previous entry) already uses — before handing it to the exporter, for every design with the override enabled. Preview and export now agree.
- Verified: exported a real 1×3 panel of the reported customer file with the override on — panel-position clustering stayed correct (3 evenly-spaced, complete 362-flash board copies, no regression from the panelization fix), and the underlying geometry is now provably mirrored (flash coordinates within each board slot shifted as expected versus the unmirrored baseline export). `tsc` clean on both touched files.

### 2026-08-18 — Fix panel-view "Fix mirror" override hiding boards on multi-PCB panels
- **Reported live**: on a real customer file (a bottom-side-only "Economy" board, all-bottom-side layers), enabling the per-design "Fix mirror" toggle and panelizing 1 row × 3 columns made the Board+Bottom preview show only the middle PCB — the outer two vanished, and the surviving board's mask border looked abnormally thick.
- **Root cause**: the per-placement counter-mirror (which cancels the panel-wide bottom-view mirror for one design) was reflecting each placement's content around the **panel's** center X instead of that **placement's own** local center X. Since `clip-path="url(#pcb-clip-N)"` is evaluated in this element's own local frame (established by its ancestors, which already include the panel-wide outer mirror, but blind to what this element's own descendants do), mirroring around the wrong axis moved two of the three boards' geometry completely outside their own clip rectangle — clipped away entirely. Only the placement whose local center coincided with the panel's center (the middle one, in a 3-wide panel) survived.
- **Fix**: the counter-mirror now reflects around the placement's own `refBounds` center, applied *inside* the position translate (so it stays within its own clip footprint) rather than the shared panel-wide axis applied *outside* it — while the real panel-wide mirror (an ancestor of every placement) still correctly repositions the whole board to its swapped panel slot afterward, exactly like every non-override placement. Fixed in both panel-view rendering paths (the composited Board view and the per-layer overlay fallback).
- Confirmed this was purely a **preview bug** — the actual exported Gerber ZIP was always correct (export code never reads the mirror-override flag at all; verified by parsing the real exported ZIP byte-for-byte: correct panel dimensions, 3 correctly-offset copies of real copper content, no corruption). Re-verified live after the fix: all 3 boards render correctly with clean mask borders in the exact same scenario that was broken.
- Also fixed a recurring **dev-server port conflict** unrelated to app code: `npm run dev` hardcoded `-p 3000`, so a second concurrent session couldn't get a free port. ### 2026-08-16 — V-groove/V-scoring alignment marks for manual depaneling machines

Verified with real keyboard input (not just synthetic events, which don't reproduce this class of bug reliably): select-all-and-retype now works normally, and clicking away from a field left empty correctly restores its prior value.

- Non-plated holes are now distinguished from plated ones. NPTH mounting holes have no pad by design, and without this the unlanded-hole check flagged them on both real test boards.
- Validated against two real boards: all four copper layers report zero clearance violations (as they should — these are manufactured designs), and the measured minimum clearance comes out at exactly 0.2000mm, matching the designer's actual KiCad setting. Annular ring was cross-checked by hand against the source files: a 0.9mm pad on a 0.4mm drill gives 0.25mm, which is what the engine reports.
- Getting there required two corrections that only real boards exposed: shapes meant to touch can land a fraction apart from coordinate rounding (leaving them wrongly on separate nets), and a pad flooded by the copper pour it connects to never touches that pour's outline. Both produced large numbers of false violations before being fixed.

### 2026-07-21 — Fix fiducials rendering as flat oversized gold dots in Board view

- First attempt used an SVG `<clipPath>` and looked correct on a small test file, but silently rendered nothing on the real board that motivated the fix — a populated board's mask layer has 1000+ shapes (one opening per pad), and this renderer's `<clipPath>` breaks down past a few hundred. ### 2026-07-21 — Fix aperture-macro corruption in exported Gerber files
- Root-caused reports of "missing D-codes" and broken RoundRect pad rendering (confirmed via tracespace.io, delta-gerber, and CAM350) to three bugs in the export path — none in tracespace, which export never touches.
- `gerber-parser.ts`: stopped uppercasing custom aperture macro names (`RoundRect` was becoming `ROUNDRECT`, so the exported `%ADD` reference no longer matched the verbatim-copied `%AM` definition — "aperture selected but never defined" in every tool). Also fixed the shape-identifier regex truncating digit-suffixed macro names like KiCad's `FreePoly0` to `FreePoly`, which spilled the trailing digit into and corrupted the first parameter.
- `panelization-engine.ts`: fixed `generateApertureDefinitions` sorting macro parameter keys (`$1`..`$10`) lexicographically instead of numerically — `"$10"` sorted before `"$2"`, shifting every corner coordinate of KiCad's RoundRect macro (10 params: radius + 8 corners + a trailing unused rotation) by one position on the way out, even though the parser had captured them correctly. Explains why CAM350 — spec-correct, no tracespace quirks — rendered the same corrupted geometry as the web viewers.

### 2026-07-20 — Excellon drill parsing fixes + rendering fixes
- Ported dead-code Excellon robustness fixes into the actual live parser (they'd never been running): Altium 9-digit coords, Allegro comment tool defs, `M00`/`M71`/`M72`, stepped `R` repeats, headerless files.
- Fixed a tool-definition regex that silently dropped every tool on files like `T1F00S00C0.024` (params before diameter).
- Added `'none'` zero-suppression mode end-to-end; added a physical plausibility check for files with no declared suppression (rejects boards smaller than their own largest drill bit).
- Fixed a freeze bug where a 2nd/3rd drill-format override silently did nothing.
- Surfaced the resolved drill format (unit/digits/suppression/tool+hole counts/source) in the Layers panel instead of discarding it.
- Patched an upstream `@tracespace/plotter` bug (via `patch-package`) that collapsed KiCad RoundRect pad side-slabs into zero-area slivers ("butterfly" pads).
- Board view substrate is now clipped to the traced board outline instead of a bounding-box rectangle, so non-rectangular boards don't show a rectangle overlapping the PCB border.
- Fixed missing copper/soldermask geometry on Proteus exports whose aperture macros wrap a primitive's point list across multiple lines — valid RS-274X, but `@tracespace/parser` silently dropped the geometry (`src/lib/gerber-preprocess.ts`).
- Fixed the board preview failing to render at all for boards with an untrustworthy traced outline (e.g. a mechanical-drawing outline that doesn't close into a real shape) — the viewBox now falls back to the union of each layer's own plotted bounds instead of tracespace's degenerate one.
- Fixed a unit-declaration bug in the Excellon normalizer: files using `M71`/`M72` (rather than bare `METRIC`/`INCH`) got their coordinates converted to mm but kept a stale inch-mode header — a self-contradictory file that fed both the preview and the actual fabrication export.
- Made the board-view compositor unit-aware: tracespace merges layers using raw native numbers with no inch↔mm conversion, so a mixed-unit set (inch-native Gerbers + a drill our pipeline re-serialized in metric — which is exactly what "Align Drill to Board Center" produces) misaligned by 25.4×, collapsing the artwork into a corner of a huge substrate. Inch-native plot trees are now scaled to mm before compositing.
- Fixed drill tool diameters surviving in inches after parsing an inch-native Excellon file (coordinates were converted to mm, apertures weren't) — "Align Drill" then re-serialized `T01C0.0240` under a METRIC header, drawing every hole as a uniform near-invisible dot.
- "Align Drill to Board Center" now recovers the drill↔Gerber origin offset **exactly** by matching the hole pattern against the copper pad pattern (vote-based algorithm ported from the MIT-licensed [delta-gerber](https://github.com/Delta-Proto/delta-gerber) project) — 315/315 holes land concentric on their pads on a real Protel relative-origin export, vs. the previous bounding-box-center approximation that left every hole ~2mm off. Falls back to copper-bounds centering when no exact match earns enough support.
